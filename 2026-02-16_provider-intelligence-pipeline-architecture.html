1. System Overview

Purpose

The Provider Intelligence Pipeline is a 5-phase data fusion system that combines CMS Medicare claims, NPPES provider registry, Google Places, and web search into unified provider intelligence for physician liaisons.

Core Value Proposition: One search query → comprehensive intelligence on every provider in a market, including independents, concierge/DPC practices, and non-Medicare providers that traditional claims data misses.

High-Level Architecture

Phase Purpose Runtime Key Output
Phase 1 Discovery Parallel queries to 4 data sources ~10-15s Raw provider lists from each source
Phase 2 Harvest URL intelligence + web scraping ~15-25s Extracted profiles, practice intelligence
Phase 3 Reconciliation Entity resolution + deduplication ~5s Unified provider records
Phase 4 Enrichment Classification + scoring ~2s Practice types, volume tiers, completeness
Phase 5 Synthesis LLM market analysis + provider cards ~15-25s Intelligence briefings, outreach priorities

Total Runtime: ~60-75 seconds for complete market analysis

Design Philosophy

  • Breadth over depth: Cast a wide net (100+ providers per source) then intelligently filter
  • Multi-source validation: Confidence increases when multiple sources confirm the same provider
  • Human-readable intelligence: Not just data dumps — synthesized insights for action
  • Specialty-agnostic: Works for any specialty through taxonomy/pattern mapping
  • Graceful degradation: Each phase is independent; failures don't cascade

2. Phase 1: Parallel Discovery

Key Insight: Run all four data sources simultaneously via ThreadPoolExecutor to minimize total latency.

2.1 CMS Medicare Discovery

Query Strategy

  1. Geography: Find all zip codes matching the city name in core_providers
  2. Specialty filtering: Match provider_type against specialty patterns (e.g., "family" → "Family Practice")
  3. Joins:
    • utilization_metrics → Medicare volume/payment data
    • raw_reassignment → Organization affiliations (PAC ID + name)
    • raw_dac_national → Group size + assignment flag
  4. Sort by: tot_medicare_payment DESC — prioritize high-volume providers
  5. Limit: Top 100 records
SELECT c.npi, c.first_name, c.last_org_name, c.provider_type, u.tot_medicare_payment, u.tot_services, u.tot_unique_beneficiaries, r."Group Legal Business Name" AS org_name, r."Group PAC ID" AS org_pac_id, d.num_org_mem AS org_member_count FROM core_providers c LEFT JOIN utilization_metrics u ON c.npi = u.npi LEFT JOIN raw_reassignment r ON CAST(c.npi AS BIGINT) = r."Individual NPI" WHERE c.zip5 IN (zip_list) AND (LOWER(c.provider_type) LIKE '%family%' OR ...) ORDER BY u.tot_medicare_payment DESC NULLS LAST LIMIT 100
Known Limitation: Specialty filtering happens BEFORE we see org affiliations. This means if you search "primary care," you won't see the 109 specialists at Torrance Memorial Medical Center — only the 1 internal medicine provider. This is provider-centric discovery, not org-centric discovery.

2.2 NPPES Discovery

Why NPPES Matters

NPPES captures all active NPIs including:

  • Concierge/DPC practices (not in Medicare)
  • New providers who haven't filed claims yet
  • Cash-only practices
  • Subspecialists with PPO-heavy panels

Query Strategy

  1. Geography: practice_city + practice_state exact match
  2. Entity filter: entity_type = '1' (individuals only, not orgs)
  3. Specialty: Match against taxonomy_1/2/3 using NPPES taxonomy codes
  4. No volume sort: NPPES has no claims data, so order is arbitrary
  5. Limit: 100 records
Design Decision: NPPES queries use city name instead of zip codes. This is because NPPES practice_city is more reliable than extracting zips from city names (avoids edge cases where a city spans multiple zips).

2.3 Google Places Discovery

Via SearchAPI.io

Uses Google Maps API proxy to search: "{specialty} near {city}, {state}"

What We Get

  • Practice names (often organizations, not individuals)
  • Addresses (for matching back to CMS/NPPES)
  • Phone, website, hours
  • Google ratings + review counts (consumer signal)
  • GPS coordinates
Places Caveat: Most results are organizations (clinics, medical groups, hospitals), not individual providers. Phase 3 reconciliation must "unpack" orgs into rosters.

2.4 Web Search Discovery

Query

"{specialty} in {city}, {state}" → Returns top 20 organic Google results

Use Case

  • Find practice websites not in Places
  • Directory listings (Healthgrades, Vitals, ZocDoc)
  • Health system provider directories
  • Blog posts / press mentions
Intelligence Value: Web results reveal narrative context — awards, specializations, reputation signals — that structured databases miss.

2.5 Parallelization Strategy

with ThreadPoolExecutor(max_workers=4) as executor: futures = {executor.submit(fn): name for name, fn in tasks.items()} for future in as_completed(futures): result = future.result() # Process as each completes

Why This Works:

  • CMS query (DB-bound) + SearchAPI (network-bound) run simultaneously
  • Total latency = max(individual_latencies), not sum(individual_latencies)
  • Each task is independent — no data dependencies between sources

3. Phase 2: Web Harvesting & URL Intelligence

Key Insight: Not all web scraping is equal. Intelligently classify URLs before deciding whether to crawl.

3.1 URL Classification

Pre-Crawl Intelligence

Before fetching any URLs, we analyze them to extract signals:

Signal What It Tells Us Action
Health System Domain Provider affiliated with UCLA, Cedars, Kaiser, etc. Tag provider with system affiliation
Directory Site Healthgrades, ZocDoc, Vitals listing Skip crawl (SPAs with poor extraction)
SPA Domain React/Vue app (no server-side HTML) Skip crawl (would need Playwright)
Path Type /doctor/name → provider profile
/location/city → practice page		 Prioritize provider profiles for harvesting
# Example URL intelligence analyze_url("https://www.uclahealth.org/providers/john-smith") → { health_system: "UCLA Health", is_spa: True, # Skip crawl path_type: "provider_profile" }

3.2 Web Scraping Strategy

What Gets Scraped

  • Independent practice websites: Small clinic sites (non-SPA)
  • Static provider profiles: Simple HTML pages
  • Practice "About" pages: Care philosophy, services offered

What Gets Skipped

  • SPAs: Healthgrades, ZocDoc, large health systems (would return empty HTML)
  • Directories: Low signal-to-noise ratio
  • Anything after the first 10 harvestable URLs: Token budget constraint
Tool Choice: Uses trafilatura library for HTML → readable text extraction. Falls back to basic regex HTML stripping if trafilatura fails.

3.3 LLM Extraction

Two Extraction Modes

Provider Profile Extraction (when page is about a specific provider):

{ "name": "full name as displayed", "credentials": "MD, DO, NP, PA, etc.", "specialty": "as listed on page", "phone": "direct line if shown", "accepting_new_patients": true/false/null, "board_certifications": [], "education": [], "languages": [], "bio_summary": "2-3 sentence summary", "conditions_treated": [] }

Practice Intelligence Extraction (when page is about a clinic/practice):

{ "practice_name": "", "clinical_services": [], "care_philosophy": "how they describe their approach", "patient_focus": "who they primarily serve", "differentiators": [], "talking_points": "briefing a liaison could use" }
Token Economics: Each page extraction costs ~$0.01 (GPT-4o, ~2K input + 500 output tokens). At 10 URLs per search, Phase 2 costs ~$0.10 per query.

3.4 Why Not Playwright?

We considered using Playwright for full SPA rendering (Healthgrades, large health systems) but decided against it:

  • Latency: +5-10 seconds per page vs. instant fetch
  • Complexity: Browser orchestration, session management, proxies
  • Diminishing returns: CMS + NPPES already cover most providers; SPAs add detail, not discovery
Strategic Decision: Use web harvest for discovery (new providers not in CMS/NPPES) and qualitative signals (care philosophy, patient focus). Save deep SPA crawling for Phase 2 feature expansion.

4. Phase 3: Reconciliation & Entity Resolution

Key Insight: Same provider appears in multiple sources with different identifiers. NPI is the Rosetta Stone.

4.1 The Entity Resolution Problem

After Phase 1-2, we have:

  • 100 CMS records (NPI + Medicare data)
  • 100 NPPES records (NPI + taxonomy)
  • 20 Google Places (no NPI, address only)
  • 10 harvested profiles (name only, no NPI)

Challenge: How many unique providers are in this set?

4.2 Six-Step Reconciliation Pipeline

Step 1: CMS Deduplication

Problem: Same NPI can appear multiple times in CMS if they have multiple org affiliations.

# Example: Dr. Philip Kim appears in 10 rows (one per org) {NPI: 1356781132, org: "Best Life Medical Group"} {NPI: 1356781132, org: "Affordable Urgent Care"} {NPI: 1356781132, org: "Singing River Health System"} ...

Solution: Group by NPI, collapse org affiliations into array, keep highest-payment record for primary data.

npi_map[npi] = { "provider": highest_payment_record, "orgs": [list of unique orgs], "max_payment": highest_payment_value }

Result: 100 CMS records → ~40 unique providers (typical dedup ratio)

Step 2: NPPES Merge by NPI

Goal: Enrich CMS providers with NPPES data (taxonomy, credentials, enumeration date)

Scenario Action
NPI exists in both CMS and NPPES Merge fields into CMS record (keep CMS as base, add NPPES taxonomy)
NPI only in NPPES (not in CMS) Create new provider record tagged ["nppes"] source
This is where we find concierge/DPC providers: NPIs with no Medicare claims (non_medicare practice type in Phase 4).

Step 3: Web Harvested Merge (Fuzzy Name Matching)

Problem: Harvested profiles have names like "Dr. Jennifer L. Chen" but no NPI.

Matching Strategy:

  1. Normalize names: strip titles, middle initials, credentials
  2. Fuzzy match against existing providers using names_match() utility
  3. Threshold: 75% confidence required for merge
  4. If no match, create new web-only provider
def names_match(name1, name2): # Strip Dr./MD/DO, normalize case # Split into first/last # Compare: # - Exact match → 1.0 confidence # - Last name match + first initial → 0.85 # - Reversed order match → 0.80 # - Fuzzy threshold (Levenshtein) → variable return (is_match, confidence)

Step 4: URL Intelligence Integration

Apply URL signals to providers:

  • If org name contains "UCLA," tag health_system = "UCLA Health"
  • If org name contains "Cedars," tag health_system = "Cedars-Sinai"
  • Store URL signals as metadata for Phase 5 synthesis

Step 5: Provider-to-Place Linking

Goal: Connect providers to their Google Places entries (for ratings, phone, website)

Matching Logic:

  1. Compare provider's street_address to each Place's address
  2. Normalize addresses (lowercase, strip punctuation, remove unit numbers)
  3. Match if: street number + street name match (70%+ confidence)
  4. Link: provider.linked_place_ids.append(place.place_id)
  5. Copy: rating, reviews, website from Place → Provider
Current Limitation: Places often represent organizations, not individuals. We link providers to Places by address, but we don't yet "unpack" a Place like "Torrance Memorial Primary Care" into its 15 individual providers.

Future Enhancement: Use raw_reassignment to find all NPIs at a Place's address, then roster them under that Place.

Step 6: Organization Graph Construction

Goal: Build the inverse view — what organizations exist, and how many providers are in each?

for each provider: for each org in provider.organizations: if org.pac_id not in org_map: create Organization(org.pac_id, org.name) org_map[org.pac_id].provider_count += 1 org_map[org.pac_id].total_beneficiaries += provider.beneficiaries

Output: List of Organization objects sorted by provider count, with totals for beneficiaries and member counts.

4.3 Reconciliation Output

By end of Phase 3, we have:

  • Unified provider list: Each provider appears once with all available data
  • Discovery source tracking: ["cms", "nppes", "web"] tags show which sources confirmed this provider
  • Match confidence: 1.0 (NPI match) down to 0.5 (fuzzy name match)
  • Organization roster: Which orgs dominate the market

5. Phase 4: Enrichment & Classification

Key Insight: Raw data becomes intelligence through classification and scoring.

5.1 Volume Tier Classification

Why Volume Matters

High-volume providers = more referrals = higher liaison outreach priority.

Percentile-Based Binning

  1. Filter providers with tot_unique_beneficiaries data
  2. Sort descending by beneficiaries
  3. Assign tiers by percentile:
    • High: Top 25%
    • Medium: 25-75%
    • Low: Bottom 25%
  4. Providers without CMS data → unknown or unknown_non_medicare
Design Choice: Percentiles are within-search, not absolute. A "high volume" provider in Beverly Hills (1,200 beneficiaries) may be "medium" in a rural area.

5.2 Practice Type Classification

Six Practice Types

Type Detection Logic Strategic Value
system_employed health_system tag exists Hard to convert, but high referral volume if you do
large_group group_assigned = 'Y' AND org member_count > 50 Decision-makers are admins, not MDs
small_group group_assigned = 'Y' AND org member_count 2-50 Partners have influence; approachable
solo_independent group_assigned = 'M' (solo Medicare) Prime targets: independent decision-making
non_medicare NPPES-only, no CMS claims Hidden gold: concierge/DPC with affluent PPO panels
group_affiliated group_assigned = 'Y' but unclear size Needs more research
# Actual classification logic if p.health_system: p.practice_type = "system_employed" elif p.group_assigned == "Y": max_members = max(org.member_count for org in p.organizations) if max_members > 50: p.practice_type = "large_group" elif max_members > 1: p.practice_type = "small_group" else: p.practice_type = "group_affiliated" elif p.group_assigned == "M": p.practice_type = "solo_independent" elif "cms" not in p.discovery_sources: p.practice_type = "non_medicare" else: p.practice_type = "unknown"

5.3 Newly Established Flag

Definition: Providers enumerated (got their NPI) within last 2 years.

Why It Matters: New providers are actively building referral networks. They're more receptive to liaison outreach than established providers.

if p.enumeration_date >= datetime(2024, 1, 1): p.newly_established = True

5.4 Completeness Scoring

Measures how much data we have about each provider (0-100%).

Scoring Rubric

Data Category Weight Components
Identity 20% NPI, name, credentials
Location 15% Address, zip
Specialty 10% CMS type, NPPES taxonomy
Volume 15% Payment, services, beneficiaries
Organization 10% Org affiliations, health system
Web Presence 10% Website exists, web-sourced data
Clinical Detail 10% Bio, certifications, languages, education
Consumer Signal 5% Google rating, review count
Contact 5% Website URL
Use Case: Low completeness score → provider needs more research before outreach. High completeness → ready to contact with intelligence in hand.

6. Phase 5: LLM Synthesis & Intelligence Generation

Key Insight: LLMs turn structured data into narrative intelligence that humans can act on.

6.1 Three Synthesis Outputs

Market Landscape Summary

Prompt Strategy: "You are a healthcare market analyst preparing a briefing for a physician liaison."

Input Data:

  • Top 60 providers (sample to fit in context window)
  • Top 20 organizations
  • Aggregate stats (practice type breakdown, volume distribution)

Output Sections:

  1. Market Overview: Total providers, practice mix, geography
  2. Health System Landscape: Which systems dominate, independent presence
  3. Volume Distribution: Where the patients are
  4. Opportunities & Gaps: Strategic insights (e.g., "15 non-Medicare providers suggest strong concierge market")
  5. Data Confidence: Completeness assessment

Provider Intelligence Cards

Goal: Generate actionable briefings for liaison outreach.

Batch Processing Strategy:

  • Sort providers by outreach score (volume + independence + completeness)
  • Process top 30 providers in batches of 5
  • 5 providers per LLM call = better quality than 30 at once
# Outreach scoring logic score = 0 if volume_tier == "high": score += 30 if volume_tier == "medium": score += 20 if practice_type in ["solo_independent", "small_group"]: score += 20 if practice_type == "non_medicare": score += 15 # Concierge opportunity if newly_established: score += 10 score += completeness_score * 10

Card Schema (per provider):

{ "one_liner": "Positioning for liaison", "outreach_priority": "high|medium|low", "priority_rationale": "Why this priority (specific numbers)", "approach_strategy": "How to approach outreach", "talking_points": ["point 1", "point 2", "point 3"] }

Example Output:

{ "one_liner": "High-volume independent primary care with 940 beneficiaries.", "outreach_priority": "high", "priority_rationale": "$900K Medicare, solo practice = full decision authority", "approach_strategy": "Lead with specialty care coordination tools; mention volume capacity.", "talking_points": [ "Large patient base with significant Medicare payments", "Diverse affiliations offering broad care opportunities", "Potential for integrated specialty care solutions" ] }

Competitive Intelligence Summary

Focus: Organization-level analysis.

  • Which groups/systems control the market
  • Independent vs. employed ratio
  • Best opportunities for penetration

Provider Cards (6 batches) GPT-4o ~3K each ~2K each $0.18
Competitive Intel GPT-4o ~2K ~1K $0.02
Total Phase 5 $0.23
Total Pipeline Cost per Search:
  • Phase 2 (web harvest): $0.10
  • Phase 5 (synthesis): $0.23
  • Grand total: ~$0.33 per market search

8. Key Design Decisions

Decision 1: Provider-Centric vs. Org-Centric Discovery

Choice Made: Provider-centric (filter by specialty first)

Trade-Off: Misses specialists affiliated with orgs in the search results. Example: searching "primary care Torrance" returns 1 provider from Torrance Memorial (the internist), not the 109 specialists also affiliated.

Mitigation: Future enhancement — add org-mode flag that pulls ALL providers at matched orgs regardless of specialty.

Decision 2: Limit 100 per Source

Rationale:
  • Search quality degrades past ~100 results (less relevant providers)
  • Reconciliation complexity scales O(n²) for fuzzy matching
  • Phase 5 LLM synthesis can't meaningfully process 300+ providers
Effect: Focus on top providers (by volume, relevance) rather than exhaustive coverage.

Decision 3: Skip SPA Crawling in Phase 2

Choice: Only scrape simple HTML sites; skip React/Vue apps and directories.

Why:
  • SPAs require Playwright → +10s latency per site
  • Healthgrades/ZocDoc don't reveal info not already in CMS/NPPES
  • Large health systems (UCLA, Cedars) are detected via org affiliation in CMS
Outcome: Phase 2 targets independent practices (most likely to have simple sites) where we find new intelligence.

Decision 4: Percentile-Based Volume Tiers (Not Absolute)

Choice: "High volume" = top 25% within this search, not a fixed beneficiary threshold.

Why: Markets vary dramatically. 1,000 beneficiaries is high-volume in Beverly Hills, low-volume in rural areas.

Implication: Volume tiers are relative to the local competitive landscape, not national benchmarks.

Decision 5: Batch LLM Processing (5 providers at a time)

Alternative Considered: Send all 30 providers in one giant prompt.

Why Batching Won:
  • Quality: LLM reasoning degrades with long context
  • Token limits: 30 providers = ~10K input tokens + 6K output = risk of truncation
  • Error handling: If one LLM call fails, we lose only 5 providers, not 30
Cost: 6 LLM calls instead of 1 = slightly more expensive but much more reliable.

Decision 6: No Real-Time Place → Provider Roster Expansion

Missing Feature: When we find "Torrance Memorial Primary Care" in Places, we don't automatically query CMS for all providers at that address.

Why Not Built Yet:
  • Address normalization is complex (suites, floors, abbreviations)
  • Would add 20+ DB queries per search (Places × CMS JOIN)
  • Most value comes from new providers, not expanding known orgs
Future Enhancement: Pre-compute address → NPI roster table in pipeline, query once per search.

9. Trade-Offs & Limitations

Current Limitations

Limitation Impact Workaround
Org-centric discovery gap Miss specialists at matched orgs Manual follow-up: "Show me all Torrance Memorial providers"
Address matching precision Some provider-Place links missed Accept ~70% link rate; manual enrichment for VIPs
No Playwright (SPA crawling) Can't extract from Healthgrades, large systems Those providers already in CMS; web adds detail, not discovery
LLM hallucination risk Synthesized intelligence may be wrong Structured output format + grounding in data reduces risk
Token budget in Phase 5 Can't process 200+ providers Sort by outreach score, process top 30
SearchAPI rate limits Phase 1 may fail if key exhausted Graceful degradation: continue with CMS/NPPES only

Scaling Constraints

Single-Threaded Reconciliation: Phase 3 is CPU-bound on fuzzy name matching. For 100+ providers × 10 harvested profiles = 1,000 comparisons.

If This Becomes a Bottleneck: Pre-compute name embeddings (sentence transformers), use ANN search instead of pairwise comparison.
LLM Latency: Phase 5 takes 15-25 seconds. If processing 100 searches/day, that's 25-40 minutes of LLM wait time.

Mitigation: Async batch processing (queue searches, process overnight) or parallel LLM calls (OpenAI allows 500 RPM).

Data Quality Issues

  • CMS data lag: Utilization metrics are 1-2 years old
  • NPPES address drift: Providers move; NPPES updates slowly
  • Google Places spam: Some listings are fake clinics (lead gen)
  • Web harvest variability: Simple sites → good extraction; old sites → poor extraction
Confidence Management: The match_confidence and completeness_score fields help users assess data quality. Low scores = "use this as a lead, verify before outreach."

Conclusion

The Provider Intelligence Pipeline is a data fusion system that combines structured databases (CMS, NPPES) with unstructured web intelligence to create actionable market insights.

Core strengths:

  • Fast (~60s end-to-end)
  • Comprehensive (finds independents + concierge providers CMS misses)
  • Actionable (not just data — intelligence cards with talking points)
  • Cost-effective (~$0.33 per market search)

Key innovation: Entity resolution across disparate sources (NPI-based + fuzzy name matching) produces a unified view that no single data source provides.

Strategic value: Transforms 4 hours of manual research into 60 seconds of automated intelligence gathering, freeing liaisons to focus on relationship-building instead of data collection.
