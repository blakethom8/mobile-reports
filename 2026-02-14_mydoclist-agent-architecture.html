🎯 Executive Summary

This manual provides a complete architectural blueprint for deploying AI agents to automate customer service and sales for MyDocList. The recommended approach is a multi-agent system with specialized roles, deployed on a dedicated Mac Mini/Studio, leveraging OpenClaw's orchestration capabilities and a customer-centric data model in Supabase. Implementation follows a phased rollout starting with reactive support, then proactive engagement, and finally advanced analytics.

1️⃣ Agent Architecture Design

Single Agent vs Multi-Agent: Analysis

Dimension Single Agent Multi-Agent
Simplicity ✅ Single context, easier to reason about ⚠️ More complex orchestration needed
Specialization ❌ Generic prompts, harder to optimize ✅ Role-specific prompts & tools per agent
Scaling ❌ Bottleneck under load ✅ Parallel execution, independent scaling
Permissions ⚠️ All-or-nothing access ✅ Fine-grained per-agent permissions
Cost ✅ Lower LLM costs (fewer calls) ⚠️ Higher costs with more parallel agents
Debugging ✅ Single log stream ⚠️ Distributed traces needed
Solo Founder Overhead ✅ Less setup/maintenance ⚠️ More infrastructure to manage

Recommendation: MULTI-AGENT

While single agent is simpler initially, a multi-agent architecture provides critical advantages for a SaaS platform: better specialization, independent scaling, and security through capability isolation. The added complexity is manageable with OpenClaw's orchestration layer, and the benefits compound as you grow.

Recommended Agent Roles

🎧 Customer Success Agent (CSA)

Primary Role: Proactive engagement, user success, retention

Capabilities:

  • Monitor user activity patterns (search frequency, feature usage)
  • Send personalized engagement emails (e.g., "We noticed you searched for pediatricians...")
  • Generate curated provider reports based on user search history
  • Track onboarding progress and send tips
  • Detect churn signals (inactivity, declining usage) and re-engage
  • Trigger in-app notifications for relevant features

Data Access: Read-only to user_profiles, user_activity_log, search_history. Write to engagement_history, agent_actions_log.

External Integrations: Email sending (via MyDocList backend API), analytics tracking

💬 Support Agent (SA)

Primary Role: Reactive customer support, bug triage, feature requests

Capabilities:

  • Monitor support inbox (support@mydoclist.com)
  • Classify incoming emails (bug, feature request, question, complaint)
  • Draft responses for common questions (password resets, data questions)
  • Auto-respond to simple queries; escalate complex issues to Blake with context
  • Log bugs to bug_reports table with severity classification
  • Log feature requests to feature_requests with user context
  • Track support thread history for context-aware responses

Data Access: Read user_profiles, email_interactions, bug_reports, feature_requests. Write to all support tables + agent_actions_log.

External Integrations: Email (IMAP/SMTP), potentially Slack for escalations

📈 Sales & Engagement Agent (SEA)

Primary Role: Lead nurturing, trial-to-paid conversion, upsells

Capabilities:

  • Track trial user behavior and engagement levels
  • Send upgrade prompts at optimal moments (power user signals, feature limit hits)
  • Generate personalized demo/case study content
  • Schedule follow-up sequences for inactive trial users
  • Track pipeline stages (trial → qualified → paid)
  • Generate weekly sales reports for Blake

Data Access: Read user_profiles, user_activity_log, engagement_history, billing_status. Write to engagement_history, agent_actions_log.

External Integrations: Email, billing API (read-only)

📊 Analytics Agent (AA)

Primary Role: Data insights, reporting, trend detection

Capabilities:

  • Generate weekly/monthly analytics reports
  • Detect anomalies (sudden drop in searches, spike in errors)
  • Identify top-performing features and underused features
  • Track cohort behavior and retention metrics
  • Generate insights for product roadmap decisions
  • Export custom reports for Blake (CSV, formatted emails)

Data Access: Read-only across all tables. Write to agent_actions_log only.

External Integrations: None (internal reporting only)

🤝 In-App Chat Agent (ICA)

Primary Role: Real-time user assistance within the application

Capabilities:

  • Answer product questions in real-time
  • Guide users through features ("How do I save a provider?")
  • Provide context-aware help based on current page/action
  • Escalate to Support Agent if unable to resolve
  • Different from backend agents—this runs client-side or via websocket

Data Access: Session-scoped user data only (current user's profile, current search context). Limited permissions.

External Integrations: WebSocket to backend, chat history DB

Security Best Practice: Each agent runs with its own Supabase service role key with row-level security (RLS) policies limiting access scope. Never use a single admin key across all agents.

Agent Coordination & Hand-offs

┌─────────────────────────────────────────────────────────────┐ │ Orchestration Layer │ │ (OpenClaw Main Agent / Coordinator) │ └───────┬──────────────────┬─────────────────┬────────────────┘ │ │ │ ▼ ▼ ▼ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ Customer │ │ Support │ │ Sales & │ │ Success │◄─►│ Agent │◄─►│ Engagement │ │ Agent │ │ │ │ Agent │ └──────┬───────┘ └──────┬───────┘ └──────┬───────┘ │ │ │ └──────────────────┼──────────────────┘ │ ▼ ┌──────────────┐ │ Analytics │ │ Agent │ │ (Observer) │ └──────────────┘

Hand-off Scenarios

  1. CSA → SA: User replies to engagement email with a question/complaint → CSA forwards to SA with full context
  2. SA → Blake: Complex bug or angry customer → SA drafts response, flags for Blake's review before sending
  3. SEA → SA: Trial user reports issue during sales sequence → SEA hands off to SA for support resolution
  4. ICA → SA: In-app chat can't resolve issue → escalates to SA email support with chat transcript
  5. AA → All: Analytics detects anomaly → notifies relevant agents (e.g., drop in engagement → CSA investigates)

🔑 Hand-off Implementation Pattern

Use a shared agent_handoffs table in Supabase:

CREATE TABLE agent_handoffs ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), from_agent TEXT NOT NULL, to_agent TEXT NOT NULL, user_id UUID REFERENCES auth.users(id), context JSONB, -- Full context data status TEXT DEFAULT 'pending', -- pending, accepted, resolved created_at TIMESTAMPTZ DEFAULT NOW(), resolved_at TIMESTAMPTZ );

Agents poll this table (or receive webhook notifications) for pending hand-offs. Context includes conversation history, user data snapshot, and specific request.

2️⃣ Customer Engagement Engine

Proactive Engagement Strategies

Use Case 1: Search-Based Engagement

Trigger: User performs 3+ searches in a session for same specialty (e.g., pediatricians)

Action: CSA sends email 24h later: "We noticed you're researching pediatricians in [City]. Here's a curated list of the top-rated providers we found, plus insights on referral patterns."

Trigger: User is active (5+ sessions) but hasn't used saved lists feature

Action: CSA sends tip: "Quick tip: You can save providers to lists for easy access later. Here's how..."

Measurement: Track feature adoption post-email

Use Case 3: Inactivity Re-engagement

Trigger: Paid user inactive for 14 days (no logins)

Action: SEA sends: "We miss you! Here's what's new in MyDocList + a quick reminder of how we can help your team hit your referral goals."

Follow-up: If still inactive after 7 days, escalate to Blake for personal outreach

Use Case 4: Power User Recognition

Trigger: User performs 50+ searches in a month

Action: CSA sends personalized recognition: "You're one of our top users! We'd love to hear your feedback. Want to schedule a quick 15-min call?" (Link to Blake's Calendly)

Goal: Gather testimonials, case studies, feature requests from engaged users

In-App Chat Agent Design

Architecture: Separate from backend agents. Runs as a service behind MyDocList's API.

Implementation Options

  1. WebSocket Service: Dedicated chat service (FastAPI + WebSockets) that connects users to ICA
    • User opens chat widget → establishes WS connection
    • Messages flow through backend to ICA (OpenClaw agent on Mac Mini)
    • ICA uses LLM to respond, with access to user session context
  2. Client-Side LLM (Future): Embed lightweight LLM in browser for instant responses
    • Privacy benefit: no data leaves user's machine for simple queries
    • Falls back to server for complex questions

ICA Capabilities

  • Contextual Help: "How do I save a provider?" → ICA knows user is on search results page, provides tailored answer
  • Feature Walkthroughs: Interactive tutorials triggered by user questions
  • Data Questions: "Where does this data come from?" → Explains NPI, Google Places sources
  • Escalation: "I found a bug" → Collects details, logs to bug_reports, notifies SA

Email-Based Interaction Model

Inbound Email Flow

1. User sends email to support@mydoclist.com 2. SA polls IMAP inbox every 5 minutes (or webhook if provider supports) 3. SA reads email + extracts: - Sender email (match to user_id in DB) - Subject + body - Thread history (via In-Reply-To header) 4. SA classifies intent using LLM 5. SA checks if auto-responder should handle or escalate 6. SA logs full interaction to email_interactions table 7. SA sends response or drafts for Blake's review

Outbound Email Best Practices

  • From Address: Use "Chief from MyDocList <noreply@mydoclist.com>" for automated emails (not "Blake") to set expectations
  • Reply Handling: Ensure Reply-To goes to support@mydoclist.com for SA monitoring
  • Personalization: Include user's name, specific activity data ("You searched for pediatricians 3 times")
  • Unsubscribe: All marketing emails must have unsubscribe link (store preferences in user_preferences table)
  • Rate Limiting: Max 1 proactive email per user per week (unless user replies, starting a conversation)

The "Deeply Engaging Customer Experience" Vision

Goal: Make every user feel like they have a dedicated account manager, even though it's automated.

Principles

  • Anticipatory: Predict user needs before they ask (e.g., "You might also want to know...")
  • Personal: Reference user's specific actions and context
  • Valuable: Every interaction must provide clear value (data, insight, time savings)
  • Respectful: Never spam; respect unsubscribe preferences instantly
  • Transparent: Users know they're interacting with AI (but it's smart AI)

Measuring Engagement

  • Email open rates (target: >30%)
  • Email reply rates (target: >5%)
  • Feature adoption post-tip emails (target: >15%)
  • Support resolution time (target: <24h)
  • Customer satisfaction scores (CSAT surveys post-resolution)

3️⃣ Data Model Design (CRITICAL SECTION)

CRITICAL This data model is the foundation of agent intelligence. Without rich user data, agents can't personalize or make smart decisions.

Core Principle: Customer-Centric Data Model

Design the database around user behavior and interactions, not just application features. Every user action should be logged and accessible to agents for context-aware decision-making.

User Profile Compilation for LLM Context

When an agent needs to make a decision about a user, it compiles a "user context snapshot" by querying multiple tables:

-- Example: CSA preparing to send proactive email SELECT up.full_name, up.company_name, up.engagement_score, up.churn_risk, up.last_login_at, -- Recent activity (SELECT COUNT(*) FROM user_activity_log WHERE user_id = up.id AND activity_type = 'search' AND created_at > NOW() - INTERVAL '7 days') AS searches_last_7d, -- Recent engagement (SELECT COUNT(*) FROM engagement_history WHERE user_id = up.id AND sent_at > NOW() - INTERVAL '30 days') AS emails_sent_last_30d, -- Support history (SELECT COUNT(*) FROM email_interactions WHERE user_id = up.id AND direction = 'inbound') AS support_emails_sent, -- Feature requests (SELECT COUNT(*) FROM feature_requests WHERE user_id = up.id) AS feature_requests_count, -- Preferences upref.email_tips, upref.preferred_engagement_style FROM user_profiles up LEFT JOIN user_preferences upref ON upref.user_id = up.id WHERE up.id = $1;

This snapshot is passed to the LLM as context: "User Sarah from HealthPlus has high engagement (score: 87), searched 23 times in the last week for pediatricians, hasn't received an engagement email in 15 days, and prefers proactive communication. Should we send a curated report?"

MCP Server for Customer Data Access

What is MCP? Model Context Protocol is an open standard (by Anthropic) that lets AI assistants access external data sources securely. Think of it like OAuth for AI agents.

Why MCP for MyDocList?

  • Future-proof: Users can connect their MyDocList data to ANY AI assistant (ChatGPT, Claude, local agents)
  • Interoperability: Data isn't locked into your platform
  • Marketing: "MyDocList is AI-native—connect your data to your own AI tools"

MCP Server Implementation

# Install MCP SDK pip install mcp # Create MCP server (mydoclist_mcp_server.py) from mcp import MCPServer, Resource server = MCPServer(name="mydoclist") @server.resource("searches") async def get_user_searches(user_id: str, limit: int = 50): """Fetch user's recent searches""" searches = await supabase.table("user_activity_log") \ .select("*") \ .eq("user_id", user_id) \ .eq("activity_type", "search") \ .order("created_at", desc=True) \ .limit(limit) \ .execute() return searches.data @server.resource("saved_providers") async def get_saved_providers(user_id: str): """Fetch user's saved provider lists""" # Implementation pass @server.tool("generate_report") async def generate_custom_report(user_id: str, report_type: str): """Generate custom reports for user""" # Calls agent to generate report pass # Run server if __name__ == "__main__": server.run(host="localhost", port=8100)

Agent-Assisted Custom Report Generation

Use Case: Salesforce Import Formatting

Scenario: User wants to export their saved providers to import into Salesforce.

Traditional Approach: Provide generic CSV, user manually maps fields.

Agent-Assisted Approach:

  1. User clicks "Export for Salesforce"
  2. AA (Analytics Agent) asks: "Which Salesforce fields do you want to map?" (or auto-detects from user's Salesforce schema if connected)
  3. AA generates CSV with exact column names matching Salesforce (Contact: First Name, Last Name, Account Name, etc.)
  4. AA adds calculated fields (e.g., "Full Address" concatenated, "Primary Phone" formatted correctly)
  5. User imports CSV directly into Salesforce with zero manual work

Other Report Types

  • Referral Pipeline Report: "Show me all cardiologists I've researched this month, sorted by referral volume"
  • Territory Analysis: "Which zip codes have I not covered yet?"

How Agents Access and Act on Customer Data

Access Pattern: Context-Aware Queries

# Example: CSA deciding whether to send engagement email # 1. Agent wakes up (via cron or heartbeat) # 2. Query for engagement candidates SELECT user_id FROM user_profiles WHERE last_login_at > NOW() - INTERVAL '7 days' -- Active users AND engagement_score > 50 -- Engaged but not power users AND user_id NOT IN ( SELECT user_id FROM engagement_history WHERE sent_at > NOW() - INTERVAL '7 days' -- Haven't emailed recently ); # 3. For each candidate, compile full context user_context = await get_user_context(user_id) # 4. LLM decision prompt = f""" You are the Customer Success Agent. Should you send a proactive engagement email to this user? User Context: - Name: {user_context.full_name} - Last login: {user_context.last_login_at} - Searches last 7 days: {user_context.recent_searches_count} - Top search topic: {user_context.top_search_specialty} - Last engagement: {user_context.last_engagement_sent_at} - Email preferences: {user_context.email_opt_in} Guidelines: - Only send if user has clear pattern (3+ searches for same specialty) - Respect preferences (check email_opt_in) - Provide value (curated insights, not generic marketing) Decision: [YES/NO] If YES, draft email subject and body. """ decision = await llm.invoke(prompt) # 5. If YES, send email and log if decision.answer == "YES": await send_email(user_id, decision.subject, decision.body) await log_engagement(user_id, "proactive_email", decision.reasoning)

Error Handling & Retry Logic

# Agents should be resilient to failures try: await send_email(user_id, subject, body) except EmailSendError as e: # Log failure await log_agent_action( action_type="send_email_failed", error_message=str(e), retry_scheduled=True ) # Schedule retry in 1 hour await schedule_retry(user_id, delay_hours=1)

9️⃣ Batch Processing Architecture

The Problem: 1,000 Emails, 1,000 LLM Calls

When you have 1,000 user emails sitting in a queue — each needing its own LLM call to classify, draft a response, or generate a personalized report — you need a purpose-built batch processing pipeline. Naive sequential processing would take hours and one failure could stall everything.

Architecture: Queue-Based Batch Processor

┌──────────────────┐     ┌──────────────────────┐     ┌─────────────────┐
│   Email Ingest   │────▶│   Supabase Queue      │────▶│   Worker Pool   │
│  (Webhook/IMAP)  │     │   batch_jobs table     │     │  (N concurrent)  │
└──────────────────┘     │                        │     │                  │
                         │  id, type, payload,    │     │  Worker 1 ──▶ LLM│
                         │  status, priority,     │     │  Worker 2 ──▶ LLM│
                         │  attempts, result,     │     │  Worker 3 ──▶ LLM│
                         │  created_at, locked_by │     │  Worker 4 ──▶ LLM│
                         └──────────────────────┘     └─────────────────┘
                                    │                          │
                                    │    ┌─────────────────┐   │
                                    └───▶│  Dead Letter Q   │◀──┘
                                         │  (3 retries max) │
                                         └─────────────────┘

Supabase Queue Table: batch_jobs

ColumnTypePurpose
idUUIDPrimary key
batch_idUUIDGroups related jobs (e.g., "morning email run")
job_typeENUMemail_classify, email_respond, report_generate, engagement_send
payloadJSONBInput data (email content, user_id, context)
statusENUMqueued → processing → completed → failed → dead
priorityINT1 (urgent) to 5 (batch). Paying users = higher priority
attemptsINTCurrent retry count (max 3)
locked_byTEXTWorker ID that claimed this job
locked_atTIMESTAMPLock timeout (stale locks auto-release after 5 min)
resultJSONBLLM output, classification, generated content
errorTEXTLast error message if failed
cost_tokensINTTokens consumed (for cost tracking)
cost_usdDECIMALEstimated cost of this job
created_atTIMESTAMPWhen queued
completed_atTIMESTAMPWhen finished

Worker Implementation Strategy

Two viable approaches for the worker pool:

Option A: Python Workers (FastAPI Background Tasks)

Add a /api/batch/process endpoint or use FastAPI's background task system. Workers poll the batch_jobs table, claim jobs with SELECT ... FOR UPDATE SKIP LOCKED, process via LLM API, write results back.

  • Concurrency: 4-8 concurrent workers via asyncio
  • Rate limiting: Token bucket per LLM provider (e.g., 60K TPM for Claude)
  • Backpressure: If queue depth > 500, reduce concurrency to avoid API rate limits
  • Pro: Lives in your existing FastAPI app, simple deployment
  • Con: Shares resources with your web API

Option B: OpenClaw Agent as Batch Worker

Dedicated OpenClaw agent with a cron job that polls the queue every 5 minutes. The agent claims N jobs, processes each as a separate LLM call within a single session, writes results back to Supabase.

  • Concurrency: Sequential within session, but can spawn sub-agents for parallelism
  • Pro: Agent can use judgment — escalate edge cases, flag unusual patterns
  • Pro: Natural integration with other agents (hand off complex cases to Support Agent)
  • Con: Slower for pure throughput; best for <500 jobs/batch

Recommendation: Hybrid

Use Python workers for high-throughput batch processing (email classification, bulk sends) and OpenClaw agents for judgment-heavy tasks (drafting personalized responses, generating custom reports). The Python worker handles the 80% that's formulaic; the agent handles the 20% that needs intelligence.

Cost Tracking & Budgeting

Every batch job logs cost_tokens and cost_usd. Create a batch_cost_summary view:

  • Daily/weekly/monthly cost aggregates by job_type
  • Per-user cost tracking (some users generate more work than others)
  • Alert threshold: if daily batch cost exceeds $X, pause non-critical jobs
  • Budget allocation per agent role (Support: $50/day, Sales: $30/day, etc.)

Failure Handling

  • Retry policy: 3 attempts with exponential backoff (30s, 2min, 10min)
  • Dead letter queue: After 3 failures, move to status = 'dead' with error details
  • Stale lock recovery: Cron job checks for locks older than 5 minutes and releases them
  • Poison pill detection: If same job fails 3x, flag for human review
  • Batch monitoring: Dashboard showing queue depth, processing rate, error rate, avg latency

🐜 Antfarm Orchestration (Multi-Agent Workflows)

What is Antfarm?

Antfarm is an open-source multi-agent orchestration layer built specifically for OpenClaw by Ryan Carson (creator of Ralph, 9.8K stars). It enables teams of specialized AI agents to execute deterministic, repeatable workflows with zero external infrastructure.

Key Properties

  • Deterministic: Same workflow, same steps, same order, every time
  • Verification built-in: Agents check each other's work (developer doesn't grade themselves)
  • Fresh context per step: Each agent runs in a clean session — no context bloat
  • Zero infrastructure: YAML + SQLite + cron. No Redis, no Kafka, no containers
  • Automatic retry: Failed steps retry; exhausted retries escalate to human
  • MIT licensed, OpenClaw-native

How Antfarm Works

│ agents:                 │        │ Agent 1: Polls for work  │
│   - planner             │───────▶│ Agent 2: Claims next step│
│   - developer           │        │ Agent 3: Verifies output │
│   - verifier            │        │ Agent 4: Tests results   │
│   - tester              │        │ Each agent = fresh       │
│   - reviewer            │        │   OpenClaw session       │
│                         │        └──────────────────────────┘
│ steps:                  │
│   plan → implement →    │
│   verify → test → PR    │

1️⃣1️⃣ Agent-to-Agent Communication Patterns

When multiple agents need to coordinate, the communication layer matters. There are three primary patterns, each with distinct trade-offs.

Pattern 1: Shared Database (Supabase)

Agent A ──write──▶ Supabase (agent_actions_log) ◀──poll── Agent B
                          │
                          ├── task_handoffs table
                          ├── agent_messages table  
                          └── shared_context table
  • How: Agents write to shared tables; other agents poll or use Supabase Realtime subscriptions
  • Pro: Simple, persistent, auditable, already in your stack
  • Pro: Full history of all agent interactions stored permanently
  • Con: Polling adds latency (5-30s); not true real-time
  • Best for: Async handoffs, batch coordination, audit trails

Pattern 2: Slack/Teams Channel as Message Bus

┌──────────────┐     ┌─────────────────────┐     ┌──────────────┐
│  Support Agent│────▶│  #agent-ops (Slack) │◀────│  Sales Agent │
└──────────────┘     │                     │     └──────────────┘
                     │  "User #1234 asked  │
┌──────────────┐     │   about enterprise  │     ┌──────────────┐
│ Analytics    │────▶│   pricing. Handing  │◀────│  CSA Agent   │
│   Agent      │     │   off to Sales."    │     └──────────────┘
└──────────────┘     └─────────────────────┘
                              │
                              ▼
                     ┌─────────────────────┐
                     │  Blake (human)      │
                     │  sees everything    │
                     └─────────────────────┘
  • How: Each agent has a Slack/Teams bot identity. Agents post to shared channels for coordination, DM each other for direct handoffs. Blake can observe all agent communication in real-time.
  • Pro: Human-in-the-loop visibility — Blake can see all agent decisions, intervene, redirect
  • Pro: Natural language coordination (agents explain their reasoning)
  • Pro: Easy to add human overrides ("@sales-agent, don't email this user yet")
  • Pro: OpenClaw already has Slack/Discord/Telegram channel support built in
  • Con: Depends on external service (Slack/Teams uptime)
  • Con: Rate limits on messaging APIs
  • Con: More expensive in tokens (agents reading channel history)
  • Best for: Human oversight, debugging agent behavior, complex handoffs requiring explanation

Example Slack Channel Structure

  • #agent-ops — All agent coordination messages (agent-to-agent handoffs)
  • #agent-alerts — Escalations requiring Blake's attention
  • #agent-logs — Verbose activity log (muted, for debugging)
  • #customer-insights — Agents share interesting findings about user behavior

Pattern 3: Direct API (OpenClaw Sessions)

Agent A ──sessions_send──▶ Agent B (direct message to session)
  • How: OpenClaw's sessions_send lets one agent message another directly
  • Pro: Fast, direct, no external dependencies
  • Pro: Built into OpenClaw natively
  • Con: No visibility for Blake unless agents also log actions
  • Con: Point-to-point (no broadcast)
  • Best for: Fast handoffs between two specific agents

Recommendation: Layered Approach

Use all three, for different purposes:

  1. Supabase (primary): All agent actions logged to database. Source of truth. Async coordination.
  2. Slack (visibility): Important decisions and handoffs posted to #agent-ops so Blake can monitor. Escalations go to #agent-alerts. This is your "control room."
  3. Direct sessions (speed): Time-sensitive handoffs between specific agents (e.g., Support → Sales for a hot lead).

Start with Supabase + Slack. The Slack channel gives you immediate visibility into what your agents are doing — critical as a solo founder. You need to trust but verify. Once you're confident in agent behavior, you can reduce Slack verbosity and rely more on database logs.

Anti-Pattern: Over-Communication

Agents chatting excessively burns tokens and adds latency. Design communication to be event-driven (only communicate on state changes) not polling-based (constantly asking "anything new?"). Each inter-agent message should carry actionable context, not just status updates.
