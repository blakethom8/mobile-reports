Optimization Recommendations

✅ High Value Docker Desktop → Colima

Savings: 6GB | Effort: Low (30 minutes)

Replace Docker Desktop with Colima, a lightweight CLI-based container runtime that uses the same Docker engine without the Electron GUI overhead.

brew install colima docker docker-compose
colima start --memory 4  # 4GB configurable limit
docker ps                # same commands, zero workflow change
docker compose up        # same compose files

Why This Works

Docker Desktop bundles a GUI, update manager, Kubernetes integration, and other features you don't use. Colima is pure Docker runtime with precise memory control. Your provider-search compose files work identically.

⚠️ One caveat: Test provider-search docker-compose with Colima first to verify compatibility (should be seamless).

✅ Easy Win Spotify Desktop → Web Player

Savings: 950MB | Effort: Trivial (bookmark)

Use https://open.spotify.com in Safari instead of the Electron desktop app. The web player is feature-complete for playback.

Trade-off: Lose desktop notifications and media key controls, but playback quality and library access are identical.

⚠️ Partial Chrome → Safari (for browsing only)

Savings: 300-500MB | Effort: Trivial (habit change)

Strategy: Safari for general browsing, Chrome only when actively developing provider-search.

Why keep Chrome for dev:

  • Chrome DevTools are industry standard for frontend debugging
  • React DevTools extension superior on Chrome
  • Network tab, performance profiling essential for provider-search work
  • Chief's browser tool requires Chrome for automation

❌ Not Recommended Cursor/Codex → Neovim + Claude Code

Potential Savings: 1.2GB | Effort: High (steep learning curve)

While this saves memory, it loses significant productivity value:

  • Cursor's inline edits and multi-file refactoring are valuable
  • Codebase awareness superior to terminal-only workflow
  • Neovim + Claude Code is powerful but requires time investment

Better approach: Close Cursor when not actively coding (same as OpenClaw app suggestion).

2. Event-Driven Triggers & Contextual Memory

Current State

Chief operates in two modes:

  • Interactive (main session): Responds to direct user messages
  • Scheduled (cron jobs): Runs isolated tasks at defined intervals

Gap: No reactive triggers based on external events (new email, git push, deployment failure, calendar event starting soon).

Proposed Enhancement: Event-Driven Trigger System

Architecture:

  1. Event Watchers: Lightweight processes monitoring:
    • File system changes (fswatch on project directories)
    • Git webhooks (push, PR opened, CI failure)
    • Email inbox (new messages matching filters)
    • Calendar (event starting in <30 minutes)
    • System notifications (Slack mention, Discord DM)
  2. Trigger Configuration File: ~/.openclaw/triggers.json 
    {
  "triggers": [
    {
      "name": "provider-search-push",
      "event": "git.push",
      "repo": "~/Repo/provider-search",
      "action": {
        "type": "cron.wake",
        "message": "Git push detected in provider-search. Run tests and verify deployment."
      }
    },
    {
      "name": "urgent-email",
      "event": "email.received",
      "filter": "from:devon@example.com OR subject:urgent",
      "action": {
        "type": "notify",
        "message": "Urgent email from Devon: {subject}"
      }
    },
    {
      "name": "meeting-reminder",
      "event": "calendar.upcoming",
      "timeframe": "30m",
      "action": {
        "type": "session.send",
        "message": "Meeting in 30 minutes: {event.title}"
      }
    }
  ]
}
  3. Contextual Memory per Trigger: When an event fires, inject relevant context:
    • For git.push → Load repo README, recent commit messages, current branch
    • For email.received → Load thread history, sender relationship context
    • For calendar.upcoming → Load event details, attendees, related project files

Implementation Path:

  1. Add triggers configuration section to openclaw.json or standalone triggers.json
  2. Create lightweight event watcher processes (fswatch, webhook listener, calendar poller)
  3. Extend cron.wake to accept event context payload
  4. Add trigger-specific memory loading (e.g., "on git.push, read ARCHITECTURE.md + CHANGELOG.md")

Memory Management Challenge

Event-driven triggers can't load all context every time (token budget). Solution: Trigger-specific context profiles

triggers.json:
{
  "name": "provider-search-push",
  "context": {
    "files": ["README.md", "ARCHITECTURE.md", "CHANGELOG.md"],
    "memory": "memory/provider-search-notes.md",
    "recent_messages": 5
  }
}

This ensures Chief wakes up with just enough context to be useful without burning tokens on irrelevant history.

3. Context-Aware Project Understanding

Current State

When working in a project directory, Chief relies on:

  • User explicitly mentioning "read the README"
  • MEMORY.md containing project background notes
  • Trial and error exploring file structure

Gap: No automatic context loading when switching between projects (provider-search vs. house-build vs. wedding planning).

Proposed Enhancement: Auto-Load Project Context

Simple Rule: "When working in a project folder, review its README first to understand the project."

Architecture:

  1. Project Registry: Maintain ~/.openclaw/projects.json: 
    {
  "projects": [
    {
      "name": "provider-search",
      "path": "~/Repo/provider-search",
      "context_files": ["README.md", "ARCHITECTURE.md", "docs/ROADMAP.md"],
      "last_active": "2026-02-12T08:00:00Z"
    },
    {
      "name": "house-build",
      "path": "~/Repo/chief/house-build",
      "context_files": ["README.md", "TODO.md", "permits/status.md"],
      "last_active": "2026-02-10T14:30:00Z"
    },
    {
      "name": "wedding",
      "path": "~/Repo/chief/wedding",
      "context_files": ["README.md", "TODO.md", "vendors.md"],
      "last_active": "2026-02-09T19:00:00Z"
    }
  ]
}
  2. Path-Based Context Detection: When user mentions a file path or cd into a directory: 
    User: "Check provider-search docker logs"
Chief (internal): "provider-search" detected → load context_files
Chief: *reads README.md + ARCHITECTURE.md*
Chief: "Provider-search is a FastAPI + React app with Supabase. Let me check the logs..."
  3. Session Workspace Tracking: When exec runs with a workdir, check if it's a known project and auto-load context if not already loaded in current session

Implementation Path:

  1. Create projects.json in workspace root (manually for now, auto-discovery later)
  2. Add project_context_load internal function that:
    • Detects current project from file paths or user message
    • Reads specified context files (README, ARCHITECTURE, TODO)
    • Injects into working memory for current session
  3. Update prompt system: "Before working with files in a registered project, load its context files if not already loaded this session"
  4. Add memory optimization: Cache project context for session duration, only re-read if files modified (check mtime)

Benefits

  • Fewer clarifying questions: Chief already knows project structure and goals
  • Accurate file operations: Knows where TODOs live, what folders contain what
  • Better decision-making: Understands project constraints (e.g., "provider-search is private" vs "learning-modules is public")
  • Smoother multi-project workflows: Context switches automatically when you do

Combined Architecture Vision

When all three improvements are implemented, Chief's workflow becomes:

  1. User mentions a task: "Fix the provider-search auth bug"
  2. Project detection: "provider-search" → auto-load README.md, ARCHITECTURE.md, ROADMAP.md
  3. Skill discovery: Check skill-index.json → github skill + coding-agent skill relevant
  4. Execute work: Read files, run commands, use appropriate skills
  5. Set up trigger: "If this fails again, trigger a wake event with Docker logs"
  6. Complete & log: Update memory/2026-02-12.md with outcome + learnings

Later, when the trigger fires:

  1. Event detected: provider-search health check fails
  2. Wake Chief with context: Load recent Docker logs + .env config
  3. Diagnose automatically: Check known issues, attempt restart
  4. Report outcome: Notify user if intervention needed, otherwise log resolution
