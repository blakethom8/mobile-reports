Salesforce Integration - Executive Summary

For: Marty Moesta, Enata | Date: February 11, 2026 | Author: Blake Thomson, Cedars-Sinai

Integration Goal

Two-part transition: Enata ingests our Salesforce data structure initially, then hosts with continuous sync via cron jobs to maintain our analytical workflows while adopting Enata's AI-enabled CRM platform.

System Overview at a Glance

5 Core Salesforce Objects
8 Database Tables
3 LLM-Enriched Tables
14 Semantic Enrichment Fields

Data Architecture

📊 Core Salesforce Data

  • sf_users - Sales reps/BD team
  • sf_accounts - Medical practices
  • sf_contacts - Healthcare providers
  • sf_activities - Tasks + Events (merged)
  • sf_task_who_relations - Many-to-many junction

🤖 LLM-Enhanced Layer

  • sf_enhanced_activities - Semantic enrichments (initiative, sentiment, intent)
  • sf_enhanced_providers - Relationship state & metrics
  • sf_activity_providers - Provider-activity network

Critical Custom Fields

MNO Prefix (Custom BD Fields): These custom Salesforce fields drive our analytics and must be preserved:

Activity Classification

  • MNO_Type__c - BD_Outreach, MD_to_MD_Visits, Events
  • MNO_Subtype_c__c - Cold_Call, Lunch, Dinner
  • MNO_Setting__c - Virtual, In-Person, Phone
  • MN_Tags__c - Initiative tags (HRBP, TACRI)
  • Attendees_Concatenation__c - Multi-provider activities

Provider Fields

  • NPI__c - National Provider Identifier
  • Specialty__c - Medical specialty
  • Geography__c - Territory assignment
  • Network_picklist__c - Network affiliation
  • Last_Outreach_Activity_Date__c - Stalled detection

LLM Enrichment Pipeline

Purpose: Extract semantic meaning from unstructured activity notes at scale

Key Enrichment Fields (14 total)

  • initiative_tag - Strategic program (HRBP, TACRI, etc.)
  • activity_intent - Purpose (First_Contact, Conversion, etc.)
  • outcome_sentiment - Positive/neutral/negative
  • relationship_stage - Pipeline position
  • strategic_value - Importance score (1-5)
  • follow_up_needed - Action required flag
  • competitor_mention - Competitive intelligence
  • mentioned_entities - Extracted physicians/practices
  • onboarding_milestone - New physician progress

Cost: ~$1 per 1,000 activities (Claude Haiku) | Processing: 500-1000 activities/hour

⚠️ Critical Nuances for Enata

1. Tasks + Events Merged into Single Table

Decision: We merge Salesforce Task and Event objects into sf_activities

Why: BD analysis treats both as "activities" — the distinction between planned (Event) and completed (Task) is less important than unified activity history

Impact: Query logic must handle type field ('Task' or 'Event') if distinction needed

2. Targeted Sync (Not Full Database)

Current approach: Only sync contacts/accounts that have activities (via TaskWhoRelation)

Benefit: ~70% reduction in database size and sync time

Trade-off: Cannot query "all providers" — only those we've engaged

Recommendation: Maintain this approach unless Enata needs full contact visibility

3. Enrichment Architecture is Portable

Current: Database-agnostic (SQLAlchemy ORM), runs as batch jobs

Options for Enata:

  • Option A: Enata hosts enrichment service (we provide code)
  • Option B: We continue running enrichment, sync enriched data to Enata
  • Option C: Hybrid — Enata provides API, we call for enrichments

Analytics & Reporting

Query Access Methods

  • MCP Server Tools - 15+ tools (foundation, analytics, intelligence layers)
  • LangGraph Agent - Natural language interface
  • Direct SQL - PostgreSQL queries
  • Chainlit UI - Web chat + data tables

Key Query Patterns

  • Initiative performance (group by initiative_tag)
  • Rep activity breakdown (filter by owner_id)
  • Provider pipeline (filter by relationship_stage)
  • Stalled relationships (days_since_last_activity)
  • Sentiment analysis (filter by outcome_sentiment)

Sync Strategy

Recommended Frequency

  • Core Salesforce data: Daily overnight sync (12am-2am PST)
  • LLM enrichments: Weekly batch (Sundays)
  • Provider aggregations: Weekly (after enrichment)

Rationale: 24-hour lag is acceptable for BD analytics (not operational). Balances freshness with API costs and processing time.

Recommended Migration Path

Phase 1 (Week 1-2): Initial ingestion, validate mappings, test sample queries

Phase 2 (Week 3-4): Dual-run validation — sync both systems in parallel, compare results

Phase 3 (Week 5): Cutover — update connection strings, disable old sync, monitor 48h

Phase 4 (Week 6+): Optimization — tune performance, integrate Enata AI features
