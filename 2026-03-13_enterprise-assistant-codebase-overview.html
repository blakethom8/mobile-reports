1. What We're Building

The enterprise assistant is a personal AI assistant for executive/VP-level users in Microsoft 365 environments. Think of it as "Chief — but for our clients." It lives inside the client's Azure tenant, connects to their Microsoft 365, and can take real actions: reading and drafting emails, managing calendar, querying data files, generating reports, and managing project pipelines.

🏗️ Deployment model: One Azure Container App per user — not per org. Each deployment is a configured instance of the same codebase. The client's data never leaves their Azure environment, which eliminates healthcare's biggest objection (security/compliance review). No BAA needed for data transit. No vendor risk assessment for hosting.

First client: Dave Devries at ASH — personal email assistant as the initial engagement, proving the model before scaling to more users.

The "OpenClaw in Azure" Pattern This system deliberately mirrors the same SOUL.md / USER.md / MEMORY.md / skills/ pattern that powers Chief locally. The agent reads AGENT.md, USER.md, and skills/*/SKILL.md from the user's OneDrive /Assistant/ folder — just like Chief reads workspace files on disk. Users can edit these files directly in their file explorer to customize the agent with zero redeploy.

3. Agent Core — The Brain

AgentLoop (packages/agent_core/loop.py)

The core loop is a standard "ReAct" pattern: send message to Claude → if tool calls come back, execute them → append results → repeat until Claude gives a text-only response or we hit 20 iterations.

Two modes: sync + streaming
  • run() — synchronous, returns AgentResponse when done. Used by /api/chat.
  • run_streaming() — async generator, yields SSE events as the agent works. Used by /api/chat/stream. This is the primary path the frontend uses.

SSE event types emitted during streaming:

Event TypeWhenKey Fields
thinkingStart of every iterationmessage
tool_startBefore executing each tooltool, label, input_summary
tool_endAfter successful tool executiontool, label, duration_ms
tool_errorAfter failed tool executiontool, error, duration_ms
text_deltaWhen Claude returns text contentdelta (the text chunk)
doneCompletionconversation_id, tokens, tool_calls_made, structured_data
errorMax iterations or fatal errormessage, code

ClaudeClient (packages/agent_core/llm.py)

Thin wrapper around the Anthropic SDK. Default model: claude-sonnet-4-20250514. Max tokens: 8192. Model can be overridden via environment var or workspace config.json (haiku / sonnet / opus tiers).

ConversationMemory (packages/context/memory.py)

Persists full conversation history to PostgreSQL. Stores both user messages and assistant responses (including tool call/result pairs). Formats history back into the Claude messages format for each new request — giving the agent true multi-turn memory.

SessionStore (packages/agent_core/session_store.py)

In-memory SQLite per conversation. Allows the agent to load CSV files from OneDrive into a local in-memory database within a conversation session, then query them with SQL. This is how data analysis works — load once, query many times, no context window overflow.

Notable Design Decisions

Large file safety guard (read_file) If a file is a CSV/TSV/XLSX and over ~15KB, read_file blocks it and returns an error instructing Claude to use load_data_file instead. Prevents context window overflow on large data files.
Bash tool Executes in /workspace (ephemeral within the container). 30s default timeout, 120s max. The agent uses this for data processing, generating HTML reports, pip installs, and calculations. Files in /workspace don't persist across container restarts — the agent must write_file to OneDrive to save anything permanently.
Draft-only email safety draft_email creates a draft in the user's mailbox but never sends. The user must review and send manually. This is by design — guards against the agent accidentally sending emails.
OneDrive path enforcement All file tools enforce that paths start with /Assistant/. This scopes the agent to its designated workspace and prevents accidental reads/writes anywhere else in the user's OneDrive.

5. The Workspace — "OpenClaw in Azure"

The workspace is a folder in the user's OneDrive at /Assistant/. It's the agent's "home directory" — just like Chief has ~/.openclaw/workspace/. The files are synced to the user's laptop automatically via Microsoft OneDrive sync.

WorkspaceReader (packages/context/workspace.py)

Reads AGENT.md, USER.md, config.json, and all skills/*/SKILL.md files from OneDrive via Graph API. These are injected into the system prompt on every request. Uses a 5-minute in-memory cache (process-level singleton) so OneDrive isn't hit on every message — only on first request or after the TTL expires.

Startup pre-warm: On container startup, the workspace is loaded once to populate the cache. This means the first user request doesn't pay the OneDrive fetch latency penalty.

Authentication

If API_KEY is set in the environment, all routes (except /api/health, /docs, /openapi.json) require an x-api-key header or api_key query param. If not set, the server warns and runs unauthenticated.

Startup Sequence (deps.py → init_clients())

  1. Load settings from environment
  2. Initialize Graph auth + email/calendar/files clients
  3. Connect to PostgreSQL, run schema migrations
  4. Initialize web client (Brave Search + Cloudflare Markdown)
  5. Initialize Claude client, workspace reader, conversation memory, session store
  6. Build AgentLoop with a tools_factory closure
  7. Pre-warm workspace cache (fetch OneDrive files on startup)
  8. Apply workspace config.json overrides (model tier, web settings)
  9. Register API key middleware (if API_KEY set)

Streaming (hooks/useChat.ts)

The frontend consumes the SSE stream from /api/chat/stream. It parses each event type and updates state accordingly — showing tool progress spinners on tool_start, updating them on tool_end, appending text on text_delta, and finalizing on done.

Tambo (lib/tambo.ts)

Tambo is the generative UI library — it allows the agent to return structured data (kanban boards, tables, charts) via the structured_data field in the done event, and the frontend renders the appropriate React component automatically. This is the "generative UI" approach — the UI is driven by data, not hardcoded screens.

Eval Framework (tests/evals/)

The eval system is a golden test harness — it sends real messages to the live endpoint, measures latency and token usage, checks that the right tools were called, and optionally scores response quality via Claude.

20 golden tasks across 5 categories:
  • simple (5) — math, greetings, capability questions. Expected: no tool calls.
  • email (4) — list emails, summarize, search, unread check. Expected: list_emails / search_emails.
  • calendar (4) — today's meetings, free/busy, week view, create event. Expected: list_events / create_event.
  • tool_chain (4) — multi-step tasks (email + calendar, read file + summarize). Tests sequenced tool use.
  • edge_cases (3) — empty message, destructive request (should refuse), multi-part interleaved request.

Results are stored in DuckDB (tests/evals/results.duckdb) so you can compare runs over time — great for catching regressions.

# Basic eval run (sync)
python tests/evals/run_evals.py \
  --url http://localhost:8000 \
  --label "local-test"

# Streaming eval (measures TTFT — time to first token)
python tests/evals/run_evals.py \
  --url https://ca-entasst-gateway-dev.... \
  --label "dev-streaming" \
  --stream

# With Claude quality scoring (needs ANTHROPIC_API_KEY)
python tests/evals/run_evals.py \
  --url https://... \
  --label "dev-quality" \
  --stream --score-quality

# Run only specific tasks
python tests/evals/run_evals.py \
