OpenClaw Teams Plugin — Codebase Analysis & Build Strategy

Date: March 10, 2026

Question: Fork OpenClaw, strip it down for Teams — or extract the good parts and build our own?

Source: OpenClaw v2026.3.8 installed locally at /opt/homebrew/lib/node_modules/openclaw/

Verdict

Don't fork OpenClaw core. Extract 6 files from the Teams plugin and build your own lightweight stack on top of @microsoft/agents-hosting — the same underlying SDK OpenClaw uses. You'll have a working Teams bot in ~500 lines of TypeScript with zero OpenClaw baggage.

1. What OpenClaw Actually Is Under the Hood

OpenClaw is a monolithic TypeScript monorepo — a personal assistant gateway with 60+ npm dependencies covering 20+ messaging channels (Telegram, WhatsApp, Discord, iMessage, LINE, IRC, Feishu, etc.). The Teams support is one plugin among many.

ComponentWhat It Is
Core runtimeGateway daemon (dist/index.js) — session management, LLM routing, tool dispatch, heartbeats, cron, canvas, TTS
Plugin SDK (openclaw/plugin-sdk/msteams)Shared types, config schema, utilities the Teams plugin imports. Tightly coupled to core.
Teams plugin (extensions/msteams/)Self-contained TypeScript module; only runtime dep is @microsoft/agents-hosting + express
60+ other extensionsdiscord, telegram, slack, whatsapp, signal, matrix, feishu, lark, line, voice, pairing, memory, TTS, etc.
Why NOT to fork OpenClaw core: The core gateway is architected for a personal single-user assistant. It has session management, heartbeat polling, cron, canvas rendering, TTS, voice calling, 20+ channel plugins, and a complex config system — none of which you need. Forking it means inheriting all that weight and ongoing merge conflicts with upstream. The core is also tightly coupled to @mariozechner/pi-agent-core (the Pi agent runtime) which is a separate opinionated system.

3. The Core Dependency — What Actually Does the Work

The single most important discovery: OpenClaw's Teams plugin has only two runtime dependencies:

// extensions/msteams/package.json
{
  "dependencies": {
    "@microsoft/agents-hosting": "^1.3.1",
    "express": "^5.2.1"
  }
}

@microsoft/agents-hosting is Microsoft's official Bot Framework SDK (the next-gen successor to botbuilder). It handles:

  • JWT signature verification for all incoming Bot Framework webhooks
  • CloudAdapter — the main adapter that processes activities (messages, events) from Teams
  • MsalTokenProvider — acquires Graph API access tokens via client credentials flow
  • Conversation references — the objects you store to enable proactive messaging

Everything else in the Teams plugin is application code layered on top of these two packages. You can use the exact same SDK directly without OpenClaw.

4. How the Pipeline Works (Traced Through the Code)

Here's the actual flow through the OpenClaw Teams plugin — no abstraction, just the code path:

// 1. Express server starts on port 3978
//    monitor.ts → loadMSTeamsSdkWithAuth() → CloudAdapter
app.post('/api/messages', async (req, res) => {
  await adapter.process(req, res, async (turnContext) => {
    await activityHandler.run(turnContext);
  });
});

// 2. CloudAdapter verifies the JWT from Microsoft's servers
//    If invalid → 401. If valid → calls your handler.

// 3. Activity handler routes by type
//    monitor-handler.ts
if (activity.type === 'message') → onMessage handler
if (activity.type === 'invoke')  → file consent handler

// 4. Message handler (your agent logic goes here)
//    monitor-handler/message-handler.ts
const text = stripMSTeamsMentionTags(activity.text);  // remove @Chief tags
const wasMentioned = wasMSTeamsBotMentioned(activity); // check RSC mention

// 5. Store conversation reference (enables proactive replies)
//    conversation-store-fs.ts
await store.save(conversationId, conversationReference);

// 6. Pass to LLM / agent logic (OpenClaw's runtime)
//    → your agent loop goes here instead

// 7. Send response
//    send.ts → messenger.ts → adapter.continueConversation()
await sendMessageMSTeams({ cfg, to: conversationId, text: response });

The Key Insight

Steps 1-3 and 7 are pure Bot Framework boilerplate — less than 50 lines. Steps 4-5 are OpenClaw's utilities (easily portable). Step 6 is where OpenClaw plugs in its LLM runtime. That's where your enterprise assistant logic goes instead.

5. Build Strategy — Your Own Stack

The right approach: new repo, clean stack. Extract the 6 useful files from OpenClaw's Teams plugin, strip the openclaw/plugin-sdk/msteams imports (they're just types + config utilities), replace with your own, and wire in your LLM/tool layer.

Your webhook.ts (Core Wiring — ~60 lines)

import express from "express";
import { loadMSTeamsSdkWithAuth, createMSTeamsAdapter } from "./sdk.js";
import { resolveMSTeamsCredentials } from "./token.js";
import { stripMSTeamsMentionTags, wasMSTeamsBotMentioned } from "./inbound.js";
import { saveConversation } from "./conversation-store.js";
import { runAgent } from "../agent/index.js";

const app = express();
app.use(express.json());

const creds = resolveMSTeamsCredentials();
const { sdk, authConfig } = await loadMSTeamsSdkWithAuth(creds);
const adapter = createMSTeamsAdapter(authConfig, sdk);

app.post("/api/messages", async (req, res) => {
  await adapter.process(req, res, async (turnContext) => {
    const activity = turnContext.activity;

    if (activity.type !== "message") return;

    // Store conversation reference for proactive messaging
    const ref = sdk.TurnContext.getConversationReference(activity);
    await saveConversation(activity.conversation.id, ref);

    // Strip @mention tags, get clean user text
    const text = stripMSTeamsMentionTags(activity.text ?? "");
    if (!text) return;

    // Run your agent
    const response = await runAgent({
      text,
      userId: activity.from.id,
      conversationId: activity.conversation.id,
      tenantId: activity.channelData?.tenant?.id,
    });

    // Reply
    await turnContext.sendActivity(response);
  });
});

app.listen(3978, () => console.log("Teams webhook ready on :3978"));

Your graph.ts (Graph API Client — adapt from OpenClaw)

// Adapted from openclaw/extensions/msteams/src/graph.ts
// OpenClaw uses @microsoft/agents-hosting MsalTokenProvider for token acquisition
// You can use the same pattern or @azure/identity ClientCredentialTokenCredential

import { ClientSecretCredential } from "@azure/identity";
import { Client } from "@microsoft/microsoft-graph-client";
import { TokenCredentialAuthenticationProvider } from
  "@microsoft/microsoft-graph-client/authProviders/azureTokenCredentials/index.js";

export function buildGraphClient(tenantId: string, clientId: string, clientSecret: string) {
  const credential = new ClientSecretCredential(tenantId, clientId, clientSecret);
  const authProvider = new TokenCredentialAuthenticationProvider(credential, {
    scopes: ["https://graph.microsoft.com/.default"],
  });
  return Client.initWithMiddleware({ authProvider });
}

7. What You Keep (and What to Watch For)

The OpenClaw Teams plugin is MIT licensed. You can copy, adapt, and use this code commercially without restriction. Just preserve attribution comments where you've directly copied non-trivial logic.

6 files to extract and adapt:

sdk.ts — ~30 lines. Load @microsoft/agents-hosting, build auth config, create CloudAdapter. Zero OpenClaw SDK imports. Copy as-is, just update import paths.
token.ts — ~50 lines. Reads appId/appPassword/tenantId from config or env vars. Has one import from openclaw/plugin-sdk/msteams (the normalizeSecretInputString utility) — replace that with a simple ?.trim() || undefined inline. Done.
inbound.ts — ~60 lines. Pure utility functions: strip <at> tags, detect bot mention, parse conversation IDs, normalize timestamps. Zero OpenClaw imports. Copy verbatim.
graph.ts — ~80 lines. Token acquisition + Graph API fetch helper. Uses MsalTokenProvider from agents-hosting for tokens. You can keep this pattern or swap to @azure/identity + the official Graph client (more ergonomic). Either works.
conversation-store-fs.ts — ~100 lines. Reads/writes msteams-conversations.json. Has some OpenClaw imports (file lock, JSON utilities) — replace those with simple fs.promises.readFile/writeFile + a JSON parse. Straightforward.
errors.ts — ~205 lines. Error classification for Teams send failures, user-friendly error messages. Minor OpenClaw type imports — easy to strip. Worth keeping for good UX on failures.

What to watch for when adapting:

  • openclaw/plugin-sdk/msteams imports — all of these are type definitions or simple utility functions. For each one, either inline the logic (~3 lines) or define your own matching type. Nothing complex.
  • getMSTeamsRuntime() calls in monitor.ts — this is OpenClaw's runtime injection (logger, config reloader). Replace with a simple console logger and your own config object.
  • OpenClawConfig type throughout — replace with your own config type: { appId, appPassword, tenantId }.

8. Your Agent Loop (What Goes Where OpenClaw's Pi Runtime Was)

OpenClaw's Teams plugin hands off to its Pi agent runtime at the message handler level. That's your extension point. Here's the shape:

// src/agent/index.ts
import Anthropic from "@anthropic-ai/sdk";
import { buildGraphClient } from "../teams/graph.js";
import { readInbox, sendEmail } from "./tools/email.js";
import { getCalendar, createEvent } from "./tools/calendar.js";
import { generateReport } from "./tools/reports.js";

const claude = new Anthropic();

export async function runAgent(params: {
  text: string;
  userId: string;
  conversationId: string;
  tenantId: string;
}) {
  // Build Graph client for this user/tenant
  const graph = buildGraphClient(
    params.tenantId,
    process.env.MSTEAMS_APP_ID!,
    process.env.MSTEAMS_APP_PASSWORD!
  );

  // Your tools (the "Claws")
  const tools = [
    readInbox(graph, params.userId),
    sendEmail(graph, params.userId),
    getCalendar(graph, params.userId),
    createEvent(graph, params.userId),
    generateReport(),
  ];

  // LLM loop (tool use pattern)
  const response = await claude.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 4096,
    system: SYSTEM_PROMPT,
    messages: [{ role: "user", content: params.text }],
    tools,
  });

  return extractTextFromResponse(response);
}

10. Decision Summary

OptionProsConsVerdict
A) Fork full OpenClaw Everything included; actively maintained 60+ deps, personal assistant architecture, tightly coupled to Pi runtime, constant upstream drift, not designed for enterprise multi-user ❌ Don't
B) Use OpenClaw as-is (just configure it) Zero build effort; already running on your machine Can't white-label; can't deploy into client Azure tenant as your product; not your IP; personal assistant UX not enterprise UX Dev only
C) Extract Teams plugin files + build your own stack 6 deps not 60; your IP; deploy into any client tenant; enterprise multi-user architecture; clean codebase you understand fully 2-3 days of extraction/adaptation work upfront ✅ Do this

Option B (use OpenClaw for your own dev environment) is actually fine — keep using it for your personal setup on this Mac Mini. But for the enterprise product you're building for clients, that's Option C: your own stack, built on the same foundation (@microsoft/agents-hosting), with the battle-tested utility code extracted from OpenClaw's Teams plugin as your starting point.
