March 30, 2026 · Architecture Report

Pretext moves text measurement out of the browser hot path

Cheng Lou's library does not replace CSS or the DOM. It changes when text analysis happens, so resize-heavy interfaces stop paying for synchronous text measurement every time application code needs geometry.

prepare() once per text/style change layout() on width changes DOM still renders the text Canvas metrics as ground truth README + STATUS + official demos reviewed
One-Sentence Model

Pretext adds a new up-front phase to UI architecture.

Instead of learning text size after a DOM layout pass, the app can precompute text geometry from cached font measurements and only use the browser for the final render.

  • Cold path: normalize, segment, measure, cache.
  • Hot path: width in, arithmetic out.
  • Browser still owns: painting, selection, accessibility, copy/paste.

01 · What Changed

Pretext matters because it turns text sizing from a reactive read into a predictive input.

The flashy demos are memorable, but the real change is architectural: the application can know a paragraph's likely height or line breaks before it asks the DOM. That is why this feels bigger than a benchmark trick.

From "measure after render" to "predict before placement"

Traditional web UI often learns text height by rendering first and then calling offsetHeight or getBoundingClientRect(). Pretext inverts that. It computes text geometry from prepared data, then lets the UI place, virtualize, or animate with that prediction already available.

It is not a CSS replacement

CSS still controls the real render. Pretext is only trustworthy when its inputs mirror CSS: same font shorthand, same line height, same white-space mode, same available width, same locale assumptions. The library is powerful precisely because it stays close to the browser's model.

It exposes missing primitives

Multiline shrink-wrap, exact pre-mount height prediction, and line-by-line routing around obstacles all feel like platform features that the web never quite shipped. Pretext packages those missing primitives into a small API surface that normal application code can use.

Critical distinction

Pretext bypasses DOM measurement, not DOM rendering. The browser still paints the text. What disappears from the hot path is the repeated question, "browser, how big did this turn out?"

02 · Flow Shift

The easiest way to understand Pretext is to compare the old loop to the new one.

This is where the CSS / JavaScript boundary becomes clear. Pretext does not eliminate browser layout. It removes repeated text-geometry readback from the loop that your app runs during resize, virtualization, and dynamic placement.

Traditional DOM Loop

CSS and the browser stay in charge, but JS keeps asking for answers too late.

1
CSS declares the text rules. Font, line height, wrapping rules, and container width live in the browser model.
2
JS mounts or updates the DOM text. The app renders first because it does not yet know the final geometry.
3
The browser computes style and layout. Line boxes and text flow become available inside the layout engine.
4
JS reads height from the DOM. Calls such as offsetHeight can force a synchronous layout flush if state changed.
5
JS positions or resizes other UI. This is where virtual lists, masonry, and transition targets get their data.
6
Repeat on every width change. The app keeps returning to the browser for text geometry, so the same expensive boundary crossing stays in the hot path.
Pretext-Enhanced Loop

JS learns enough up front that repeated layout becomes arithmetic instead of DOM readback.

1
CSS still defines the real render. The app mirrors the same typography contract into JS: font, line height, white-space mode, locale.
2
prepare() runs when text or text rules change. It normalizes content, segments it, measures widths via canvas, and returns reusable prepared data.
3
Resize or layout state provides only width. The app now needs a number such as contentRect.width, not DOM text measurement.
4
layout() computes height and line count. The hot path is just line-breaking math over cached widths.
5
JS uses those numbers to place UI. Virtualization, transitions, occlusion, and scroll anchoring can all use the predicted geometry.
6
The browser paints normal text. Accessibility, selection, find-in-page, and copy/paste remain intact because the final text can still live in the DOM.

Moved up front

  • Whitespace normalization
  • Locale-aware segmentation
  • Bidi-sensitive text analysis
  • Canvas width measurement
  • Cache creation for later reuse

Kept in the hot path

  • Receiving the current available width
  • Greedy line breaking over cached widths
  • Returning height and lineCount
  • Applying positioning or sizing logic

Still browser-owned

  • Actual DOM rendering and paint
  • Selection, accessibility, clipboard behavior
  • CSS cascade and style resolution
  • Final visual correctness of the rendered text
03 · Up-Front Work

What prepare() front-loads is the whole story.

The README frames prepare() as the one-time pass and layout() as the cheap hot path. That division is the main mental model to keep. If you blur them together, the value proposition becomes fuzzy.

1. Normalize the text model

Pretext starts by deciding what kind of whitespace behavior you want. The default target is the normal browser-style text model, and the README exposes { whiteSpace: 'pre-wrap' } when spaces, tabs, and hard breaks need to stay visible.

2. Segment for real languages, not just spaces

This is why the library is more serious than a toy demo. It uses Intl.Segmenter, grapheme-aware processing, bidi handling, and glue rules instead of pretending that line breaking is just text.split(' ').

3. Measure widths with canvas

The core trick is to use canvas.measureText() against the browser's font engine as the metric source, while staying outside normal DOM layout readback. That gives the library numeric text widths without asking the layout engine to re-measure a rendered node.

4. Return an opaque prepared handle

The prepared object is not a convenience value; it is the expensive state. Cache it by text, font, locale, and white-space mode. Recreating it on every resize or rerender throws away the architecture.

04 · CSS vs JS

Pretext works when CSS and JavaScript agree on a shared contract.

This is the deeper flow question underneath the demos. CSS still owns the visible result. JavaScript is only borrowing enough of the browser's text model to make geometry decisions earlier.

Concern Browser / CSS Role Pretext Role If They Drift
Font shorthand CSS decides family, size, weight, style, and actual font fallback. You pass the same font string into prepare(). Widths stop matching. Prediction quality drops immediately.
Line height The browser paints each line with the declared line-height. You pass the numeric line height into layout(). Height and line count math no longer map cleanly to the DOM result.
Whitespace and wrapping CSS controls wrapping semantics. The README targets white-space: normal or opt-in pre-wrap, with word-break: normal, overflow-wrap: break-word, and line-break: auto. Unsupported text settings can create mismatch between prediction and render.
Available width Layout systems or CSS determine how much inline space exists. You feed that width to layout(), ideally from a resize signal such as ResizeObserver. If the wrong width is used, the predicted line breaks will be wrong even if measurement is perfect.
Final rendering The browser still draws text, caret positions, selection, and accessibility behavior. Pretext predicts or manually routes lines. It does not replace the browser's final paint stage. If you assume it is a full rendering engine, you will oversell what the library actually does today.
Custom line routing CSS provides standard flow, columns, floats, and a fixed set of layout primitives. Manual APIs such as layoutWithLines() and layoutNextLine() let application code route lines around obstacles or choose better widths. If you keep thinking in pure CSS terms, the deeper capabilities never show up.

Keep these synced

  • Use a named font and pass the same shorthand string into Pretext.
  • Match the numeric line-height you actually render with.
  • Treat locale as part of the cache key when segmentation behavior matters.
  • Use the real available width from your layout system, not a guess.

When CSS is still the right answer

  • Static text with ordinary wrapping and no pre-render geometry requirements
  • A handful of one-off elements where a DOM read is not on a critical path
  • Interfaces that do not virtualize, occlude, or animate to exact text heights
  • Cases where the simplest solution is to let the browser do all the work
05 · API

The public API maps cleanly onto two application patterns.

The first pattern predicts height for normal DOM UIs. The second takes control of line routing for canvas, SVG, or editorial-style custom layout. The difference is not just convenience level; it is a difference in who owns the line flow.

Pattern A: predict geometry for DOM text

Use prepare() once and layout() whenever width changes. This is the path for virtualized lists, exact height animations, occlusion, and any UI where text size must be known before or during placement.

Pattern B: route lines yourself

Use prepareWithSegments() plus layoutWithLines(), walkLineRanges(), or layoutNextLine() when application code needs the lines themselves rather than just height and count.

import { prepare, layout } from '@chenglou/pretext'

const font = '500 16px "IBM Plex Sans"'
const lineHeight = 24
const cache = new Map()

function preparedFor(text) {
  const key = `en-US::${font}::${text}`
  let prepared = cache.get(key)
  if (!prepared) {
    prepared = prepare(text, font)
    cache.set(key, prepared)
  }
  return prepared
}

const ro = new ResizeObserver(entries => {
  for (const entry of entries) {
    const node = entry.target
    const width = entry.contentRect.width
    const prepared = preparedFor(node.dataset.copy)
    const { height, lineCount } = layout(prepared, width, lineHeight)

    node.style.setProperty('--predicted-height', `${height}px`)
    node.dataset.lineCount = String(lineCount)
  }
})

// Content change => rerun prepare()
// Width change => rerun layout()

The important split

Rerun prepare() when the text, font, locale, or white-space mode changes. Rerun layout() when width changes. That split is the entire performance strategy.

Why this changes UI flow

The app can now size containers or compute list positions before mounting all text into measurable DOM nodes. That is what removes layout thrash from resize-heavy paths.

import { prepareWithSegments, layoutNextLine } from '@chenglou/pretext'

const prepared = prepareWithSegments(
  'Wrap this headline around a chart annotation and a pull quote.',
  '700 28px "Space Grotesk"'
)

let cursor = { segmentIndex: 0, graphemeIndex: 0 }

for (const slot of lineSlots) {
  const line = layoutNextLine(prepared, cursor, slot.width)
  if (line === null) break

  drawText(slot.x, slot.y, line.text)
  cursor = line.end
}
The quietly radical API

walkLineRanges() is one of the most interesting parts of the README. It lets you test widths without building strings, which is why the bubble demo can binary-search for the tightest width that preserves the same line count. That is a new primitive, not a small convenience feature.

07 · Use Cases

The strongest use cases are the ones where text geometry drives application logic.

This is where the report needed more range. Chat bubbles are one example, but the more interesting cases are the ones where text shape decides placement, testing, or composition before the browser can hand back a measured DOM node.

Virtualized feeds with mixed-length content

Knowledge feeds, issue streams, comments, notes, and support threads all benefit when item height is known before full mount. Pretext lets virtualization use predicted geometry rather than guesstimates plus correction.

Copy-fit checks in CI or local tooling

The README explicitly points at browser-free verification for overflow. That is unusually relevant in AI-assisted workflows, localization, and design systems where generated labels need to fit before someone opens a browser.

Card packing, occlusion, and board layouts

Dashboards, market boards, editorial cards, and marketplace tiles often need text height to determine placement. Pretext turns those systems into one-pass decisions instead of mount-measure-reflow cycles.

Obstacle-aware narrative layouts

Flow text around images, charts, annotations, or pull quotes without waiting for browser layout reads. This is the bridge from ordinary app UI into layout systems that feel closer to a tiny composition engine.

Width-tight UI elements

Message bubbles, hints, labels, map callouts, and assistant responses often look better when the box hugs the paragraph more tightly than CSS can manage. Pretext provides that missing shrink-wrap control.

Shared text logic across DOM, canvas, and SVG

When a product mixes DOM UI with non-DOM surfaces, the same prepared text can drive height prediction in the DOM and line routing on canvas or SVG. That reduces the need for separate text systems per surface.

Nuance on AI and streaming UIs

Pretext is strong for preflight checks, generated-copy validation, post-update re-anchoring, and batched content changes. A naive per-token streaming loop that reruns prepare() on every token would throw away much of the advantage. The architecture rewards batching and reuse, not constant cold-path work.

08 · Caveats

The README and status docs are careful about scope, and the report should be too.

This is not "replace the browser with math." It is a deliberately bounded text-measurement and line-layout system. The limits are part of why the idea is credible.

It is not a full font rendering engine

The README says that directly. Pretext targets a common text setup, not every possible typographic feature on the platform. That is the right scope for a library trying to stay small and fast.

Text-model assumptions matter

Current targets include white-space: normal, word-break: normal, overflow-wrap: break-word, and line-break: auto, with opt-in pre-wrap. If your CSS diverges from those rules, you need to test carefully.

Named fonts matter

The README warns that system-ui is unsafe for layout() accuracy on macOS. That is a concrete reminder that font fallback and platform font behavior are not trivial details here.

Hot-path speed depends on amortization

For one small text block measured once, CSS or a normal DOM read is often simpler. Pretext pays off when the same prepared state is reused across resize, virtualization, or repeated layout decisions.

Status tracking is unusually serious

STATUS.md points to browser accuracy sweeps, benchmark snapshots, and a regression-gate mindset. That helps explain why experienced frontend engineers are taking it seriously rather than treating it as demo magic.

Server-side is still future-facing

The README describes server-side rendering as "soon" or "eventually" rather than as the main current path. That means the strongest current story is still browser-based apps and alternate browser surfaces such as canvas or SVG.

09 · Why It Lands

Why people are so impressed by this, beyond the demos.

This section is an inference from the README, STATUS docs, official demos, and the scale of public repo response. Direct X indexing was unreliable, but the reasons the project resonates are fairly legible.

It exposes a primitive the platform never gave us

Developers have long wanted exact multiline sizing and tighter width control without DOM probing. Pretext feels impressive because it turns a long-standing absence in the web platform into a usable library API.

It keeps the DOM benefits

A lot of "custom text engine" ideas throw away accessibility and selection. Pretext is compelling because the DOM can still be the final renderer, so the browser keeps the human-facing behaviors while JS gets earlier geometry.

It handles hard text, not toy English

Mixed bidi, emojis, segmentation, and browser quirks are front and center in the docs. That seriousness signals that the library is attacking the real production problem, not a benchmark optimized for plain ASCII.

It makes an invisible optimization visible

Dragons, ASCII particles, and rich compositions spread because they make the underlying engine legible. The spectacle is not the point, but it is an effective delivery vehicle for a pipeline change most users would otherwise never notice.

It suggests a better frontend workflow

The deepest appeal is workflow-related: text fit, line breaks, and layout choices can become deterministic data earlier in the pipeline. That is especially interesting in tooling, AI-assisted UI work, and any product where text geometry drives placement logic.

It is cleanly conceptualized

Good engineers notice when a library has a crisp boundary: cold-path analysis, hot-path arithmetic, browser as renderer. The clearer that model is, the easier it is to trust and adopt.

10 · Takeaways

The decision rule is simple: use Pretext when text geometry is part of your application logic.

If the browser can happily own the whole problem, let it. Reach for Pretext when text size is no longer just a visual consequence and becomes an input to placement, virtualization, composition, or validation.

Use plain CSS / DOM when...

  • Text is ordinary and a few one-off DOM reads are not on a critical path.
  • You do not need geometry before render or during frequent resize loops.
  • The browser's default flow is already the whole solution.
  • Simplicity matters more than adding another text contract to the codebase.

Use Pretext when...

  • Text height decides virtualization, occlusion, animation targets, or placement.
  • You need repeated width-sensitive layout without repeated DOM text measurement.
  • You want width-tight multiline elements or obstacle-aware text flow.
  • You need browser-like text geometry in JS tooling, tests, or alternate surfaces.
The deeper point

Pretext changes when your application is allowed to know text geometry. That up-front phase is the real innovation. The accordions, bubbles, editorial layouts, and social-media demos are downstream consequences of that single shift in flow.
