🔴 The 30-Year Problem: Layout Reflow

Every time you ask a browser how tall a block of text is, you pay a hidden tax. Pretext is the first library to eliminate it at scale.

30ms+

Cost of Layout Thrashing on a 500-Item List

When UI components independently call getBoundingClientRect() or offsetHeight on 500 text blocks, the browser must synchronously recompute the entire document layout for each read. That's 30ms+ per frame — well past the 16.6ms budget for 60fps.

🛑 The DOM Measurement Loop (Old Way)

The traditional approach for dynamic text sizing:

  1. Insert element into DOM
  2. Call getBoundingClientRect()
  3. Browser pauses: recomputes layout
  4. Returns height
  5. Repeat × 500 items = 500 reflows

Result: Main thread blocked. Visual stutter. Bad UX.

✅ The Pretext Insight

canvas.measureText() uses the same font engine as DOM rendering but operates outside the browser's layout process entirely.

  • Measure word widths via canvas once
  • Cache those widths per font config
  • From then on: layout = pure arithmetic
  • No DOM reads. No reflows. Ever again.

Result: 0.09ms for 500 text blocks. Zero layout recalculations.

"The problem is forced layout recalculation, where the browser has to pause and re-measure the page layout before it can continue. When a UI component needs to know the height of a block of text, the standard approach is to measure it from the DOM. Do this for 500 text blocks in a virtual list and you've forced 500 of these pauses. This pattern, called layout thrashing, remains a leading cause of visual stuttering in complex web applications."

— dev.to/denodell, "You're Looking at the Wrong Pretext Demo"

prepare() — The Expensive Pass (Once)

Does all the hard work upfront, returning an opaque PreparedText handle:

  • Normalize whitespace — handles tabs, hard breaks, unicode spaces
  • Segment with Intl.Segmenter — locale-aware word boundaries for every language
  • Bidirectional text — mixed English/Arabic/Hebrew/RTL handled correctly
  • Canvas font measurement — actual font engine widths, cached per segment
  • Returns opaque handle — pass to layout() as many times as needed

⚠️ Never call prepare() again for the same text + font — that defeats the caching.

layout() — The Fast Path (Repeated)

Pure arithmetic over cached widths. Called on every resize, scroll, or container change:

  • Walk cached widths — no DOM, no canvas, just numbers
  • Track running line width — insert line breaks when maxWidth exceeded
  • Returns height + lineCount — the data you need for virtualization
  • 0.09ms for 500 items — fast enough for 120fps without batching

✅ Safe to call in animation frames, resize observers, and scroll handlers.

Why canvas.measureText() Works as a Ground Truth

Browsers use the same font engine for both canvas text rendering and DOM text rendering. When you call canvas.measureText('Hello'), you get the exact same width the browser would use when laying out a <span>Hello</span> in the DOM — but without triggering the layout system. Pretext exploits this equivalence to build a pure-math layout engine that produces results identical to the browser's own engine. Cheng Lou explicitly validates against the browser as the ground truth, which is why the library is described as "very AI-friendly" — you can iterate on layout logic in a deterministic, reflow-free environment.

🔧 The API Surface

Pretext offers two use-case tiers: simple height prediction, and full manual line layout.

Use Case 1: Height Prediction

The most common pattern — predict text height before DOM insertion for virtualization and positioning.

Use Case 2: Manual Line Layout

Full control over line routing — for canvas, SVG, WebGL, server-side rendering, and complex editorial layouts.

// ── USE CASE 1: Height Prediction (DOM rendering) ──────────────────────────

import { prepare, layout } from '@chenglou/pretext'

// One-time setup per unique (text, font) combination
const prepared = prepare('AGI 春天到了. بدأت الرحلة 🚀', '16px Inter')

// Hot path: call on every container resize, zero reflow
const { height, lineCount } = layout(prepared, containerWidth, lineHeight)

// Pre-wrap mode for textarea content
const preparedPre = prepare(textareaValue, '16px Inter', { whiteSpace: 'pre-wrap' })
const { height: preHeight } = layout(preparedPre, containerWidth, 20)


// ── USE CASE 2A: Line-by-Line (canvas, SVG, WebGL) ─────────────────────────

import { prepareWithSegments, layoutWithLines } from '@chenglou/pretext'

const prepared = prepareWithSegments('Hello world. 你好世界.', '18px "Helvetica Neue"')
const { lines } = layoutWithLines(prepared, 320, 26)

// Render to canvas:
for (let i = 0; i < lines.length; i++) {
  ctx.fillText(lines[i].text, 0, i * 26)
}


// ── USE CASE 2B: Width-tight "shrink wrap" ─────────────────────────────────

import { walkLineRanges } from '@chenglou/pretext'

let maxW = 0
walkLineRanges(prepared, 320, line => {
  if (line.width > maxW) maxW = line.width
})
// maxW = tightest container that still fits — "multiline shrink wrap"
// This has been missing from the web for 30 years.


// ── USE CASE 2C: Variable-width lines (float around images) ────────────────

import { layoutNextLine } from '@chenglou/pretext'

let cursor = { segmentIndex: 0, graphemeIndex: 0 }
let y = 0

while (true) {
  // Lines beside the image are narrower
  const width = y < image.bottom ? columnWidth - image.width : columnWidth
  const line = layoutNextLine(prepared, cursor, width)
  if (line === null) break
  ctx.fillText(line.text, 0, y)
  cursor = line.end
  y += 26
}

⚠️ Critical Usage Note: prepare() is Expensive

Never call prepare() in a loop or on every render. The pattern is:

  • prepare() — once, when text content changes (new message loaded, content edited)
  • layout() — every time the container resizes, scrolls, or rerenders

Calling prepare() on every resize defeats the entire architecture and will be slower than the DOM approach.

🎯 Key Takeaways

What this means for how we build web UIs — now and going forward.

1. Layout Thrashing Has a Solution

For 30 years, "how tall is this text?" required a DOM read. That's no longer true. Pretext decouples text measurement from the browser's layout engine, eliminating an entire class of performance problems.

2. The Hot Path is the Point

prepare() once, layout() forever. The architecture is designed for resize-heavy, scroll-heavy, AI-streaming UIs where layout is called thousands of times per session. That's where the 500× improvement compounds.

3. Accessibility is Preserved

Unlike Canvas-only approaches, Pretext predicts height for DOM text nodes. The text still lives in the DOM — screen readers, selection, copy/paste, find-in-page, and translation all work exactly as before.

4. AI UIs are a First-Class Citizen

Deterministic, browser-free layout makes Pretext ideal for AI-generated and AI-streaming UIs where you need to know layout before the text is rendered. Lou explicitly calls this out in the README.

5. Multiline Shrink Wrap is Finally Possible

walkLineRanges() returns the widest line, enabling "shrink wrap" — the tightest container width that fits multiline text without overflow. This layout primitive has been missing from the web since its inception.

6. The Viral Demos Obscured the Real Story

Dragons and ASCII smoke went viral. The measurement engine that enables production-grade virtualization, masonry, and accordion layouts went mostly unnoticed. The most impactful features aren't always the most visual.

The Bottom Line

Pretext doesn't replace React, CSS, or the DOM. It removes one specific, expensive operation — text height measurement — from the browser's layout pipeline and replaces it with pure arithmetic. For any app with dynamic text in complex layouts (virtual lists, masonry, accordions, AI UIs), this is a step-function improvement in performance and correctness. 15KB. Zero dependencies.
