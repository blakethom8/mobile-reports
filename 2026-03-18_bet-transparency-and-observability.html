🔍 Bet Transparency & Observability Architecture

Prepared by Chief | March 18, 2026

How the system will explain, review, and improve every bet decision

Goal: no black-box bets. Every bet should be auditable before, during, and after execution so a human or coding agent can understand exactly why it happened and whether we should do it again.

Why This Matters

A profitable-looking system can still be fragile if it cannot explain itself. We want the opposite: a system that records enough evidence that future-you — or a coding agent — can diagnose whether a bad result came from forecast error, market microstructure, bad sizing, bad timing, or simple bad luck.

The five questions every bet should answer

  • What did we think the real-world probability was?
  • What was the market offering at that moment?
  • Why did we believe there was edge?
  • What execution assumptions did we make?
  • What happened afterward, and what did we learn?

The Bet Explanation Funnel

Forecast belief → Fair probability → Market comparison → Executable edge → Order → Outcome → Review

If we only log the order, we lose almost all the context. The system should preserve the whole chain.

Dashboard Views We Should Eventually Build

1. Pipeline Health

  • last successful ingest by source
  • row deltas by job
  • stale source alerts
  • failed parse counts

2. Live Candidate Bet Feed

  • top current edges
  • skipped bets and abstention reasons
  • confidence distribution
  • execution constraints blocking otherwise good bets

3. Bet Detail Page

  • market price over time
  • forecast revisions over time
  • sibling-bucket distribution snapshot
  • decision rationale panel
  • fill and fee details

4. Review / Learning Page

  • expected vs realized edge
  • performance by city, horizon, and signal version
  • top failure modes
  • recommendations for threshold updates

Structured Review for Self-Healing

The point is not just transparency. It is a review loop.

Post-trade review categories
  • Model wrong — fair probability estimate was bad
  • Execution bad — edge existed, but we paid it away
  • Market stayed irrational — timing target failed
  • Source mismatch — forecast/settlement alignment problem
  • Risk rule issue — size or threshold logic was off

What This Enables

  • A human can inspect why a bet happened
  • A coding agent can review bad bets and propose improvements
  • We can distinguish signal problems from execution problems
  • The system can become self-improving without becoming self-delusional
