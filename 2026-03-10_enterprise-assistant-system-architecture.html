Core Design Principle

One deployment per client organization. Every user in that org shares the same agent infrastructure but has their own isolated context, memory, and data access. Their data never leaves their Azure tenant. You manage the template; they own the instance.

Part 1 — Deployment Model: Per-Org, Not Per-User

The instinct from the March 8 architecture session was "one server per person." The refined model is one deployment per client organization — with user isolation handled inside the application, not at the infrastructure level. This is cleaner, cheaper, and easier to manage.

Part 2 — The Context Repository (The Brain)

This is the most important architectural decision. Every user in the org shares one agent, but the agent has two tiers of context: what it knows about the organization, and what it knows about you personally.

Tier 1 — Org Context (Shared Across All Users)

Managed by: Admin / IT / You during onboarding

The "Agent Data Catalog" — the shared brain for the whole organization. Think of it as the org's institutional knowledge, structured for AI consumption.

  • Org Catalog — business rules, KPIs, data source descriptions, reporting standards, acronyms
  • People directory — org chart, roles, email addresses, who owns what (synced from Graph API)
  • Report templates — the formats, styles, and structures for standard deliverables (monthly board report, market share pull, physician liaison update)
  • Data connections — what databases/APIs are available, how to query them, what the fields mean
  • Workflow definitions — standard processes (how to escalate an issue, what approval flows exist)
  • Access control rules — which users can trigger which tools (not everyone gets SQL access)

Tier 2 — User Context (Personal, Per-User)

Managed by: The individual user (private)

Each user's private context — their memory, their patterns, their preferences. Completely isolated from other users.

  • Long-term memory — significant decisions, preferences, recurring requests, relationships they care about
  • Email patterns — who they care about, how they communicate, common response styles, people to filter out
  • Report history — past reports generated, what they liked/changed, their data preferences
  • Calendar preferences — scheduling rules, meeting habits, focus time blocks
  • Active projects — what they're currently tracking, open loops

Context Repository Storage Design

PostgreSQL (in Azure, within client's tenant)
├── org_context table
│   ├── id, org_id, category, key, value, updated_at, updated_by
│   └── (catalog entries, templates, data source configs, people)
│
├── user_context table
│   ├── id, org_id, user_id (AAD object ID), key, value, updated_at
│   └── (preferences, active projects, flags)
│
├── user_memory table
│   ├── id, org_id, user_id, content (text), embedding (vector), importance, created_at
│   └── (long-term memory entries, semantically searchable)
│
├── sessions table
│   ├── id, org_id, user_id, conversation_id, channel, messages (jsonb), updated_at
│   └── (conversation history per channel/thread)
│
└── audit_log table
    ├── id, org_id, user_id, action, resource, metadata, timestamp
    └── (IT compliance: every agent action logged)

Context Management Interface

Users and admins manage context through the Web App dashboard (not by editing raw database rows). The agent also updates context automatically as it learns:

Part 4 — The Three Channels

Channel 1: Microsoft Teams Bot (Primary)

  • Use: Conversational — quick requests, inbox triage, alerts, ad-hoc queries
  • Auth: Azure Bot Service JWT → user identified by AAD object ID → loads their User Context
  • Scope: Personal DMs (the core use case) + channel mentions (team-level queries)
  • Proactive: Agent can push morning briefs, meeting alerts, report readiness notifications
  • Implementation: Adapted from OpenClaw Teams plugin (the 6-file extraction discussed earlier)

Channel 2: Web App Dashboard

  • Use: Rich interface — view reports, manage context, admin panel, report history, settings
  • Auth: Azure AD OAuth2 (same credentials as Teams/M365 — SSO, no new password)
  • Key views:
    • Home — daily brief, active tasks, recent reports
    • Reports — generated report library, request new report, schedule recurring
    • Inbox — email triage view (what agent surfaced, approve/edit drafts)
    • Context — view/edit your personal context + org catalog (admin only)
    • Admin — user management, audit logs, data connections, access control
  • Tech: Next.js + Azure Static Web Apps (or Container App) + Tailwind
  • Also has a chat widget — full conversational access from the web, same agent as Teams

Channel 3: Email

  • Use: "Send an email to your assistant" — for users who prefer email or are on mobile without Teams
  • How it works: Agent monitors a dedicated mailbox (e.g., chief@[clientdomain].com) via Graph API webhooks. Inbound email → agent processes → replies from same mailbox.
  • Use cases: "Forward this email and tell me how to respond." / "Generate the monthly report and email it to me."
  • Auth: Graph API delegated auth — only emails from whitelisted users in the org are processed

Part 6 — The Agent Loop (How It All Connects)

User sends message (Teams / Web / Email)
         │
         ▼
Channel Handler (teams/webhook.ts or email/handler.ts)
  → Extract: userId (AAD), conversationId, text, channel
  → Authenticate: verify this user is in allowlist
         │
         ▼
Session Manager
  → Load conversation history (last N messages)
  → Load user's active context (what are they working on?)
         │
         ▼
Context Loader
  → Fetch Org Context (catalog, templates, relevant sections)
  → Fetch User Context (preferences, memory, current projects)
  → Assemble system prompt: [org knowledge] + [user memory] + [available tools]
         │
         ▼
Agent Core (LLM Loop)
  → Call Claude with: system prompt + conversation history + user message + tool definitions
  → If tool use: execute Claw, feed result back, continue loop
  → If done: return final text response
         │
         ▼
Memory Writer (async, after response)
  → Check if anything notable happened → write to user_memory if yes
  → Update user_context (e.g., "active project" tracking)
         │
         ▼
Channel Responder (send back to originating channel)
  + Audit Logger (log action to audit_log table)

Part 7 — Multi-User Session Management

Multiple users in the same org hitting the same container — here's how they stay isolated:

LayerKeyIsolation
Teams sessionAAD Object ID (from JWT)Each user's conversation is their own thread in the DB
Email sessionSender email address → resolved to AAD userIdSame user ID system
Web sessionAzure AD OAuth2 token → userIdSSO, same identity as Teams
User contextorg_id + user_id composite keyAll DB queries scoped to both
Email accessDelegated Graph token per userAgent can only read that user's email — not org-wide
Audit loguser_id on every rowAdmin can filter by person
Key security point for IT reviews: The agent accesses each user's email and calendar using delegated permissions tied to that user's AAD identity — not application-wide access. This means the agent can only read what that user has access to. Admins can revoke an individual user's access without affecting others.

Part 8 — Business Model

This is a high-touch, embedded relationship business. You're not selling a subscription to SaaS software — you're deploying a managed AI brain for an executive team and maintaining it. That's a fundamentally different product.

The Compounding Dynamic

Every client deployment strengthens the product:

  • Better report templates (add to your library)
  • More Claw patterns (reusable across clients)
  • Faster onboarding (tighter playbook each time)
  • Better Org Catalog methodology (you know the right questions to ask)

Part 9 — Open Source Strategy

The Answer: Open the Shell, Keep the Brain

Don't open source the whole platform initially. Open source the Teams channel connector layer only — then keep the Claw library, context system, and healthcare intelligence proprietary. This is the same model OpenClaw uses: open platform, monetize on expertise and services.

ComponentOpen Source?Why
Teams channel connector (packages/channels/teams/)Yes — eventuallyDrives discovery, IT team trust, community. Doesn't expose your moat.
Core agent loop (packages/agent-core/)NoYour LLM orchestration patterns are IP
Claw library (packages/claws/)NoThe tool implementations are the product
Context repository design (packages/context/)NoThe Agent Data Catalog methodology is the moat
Healthcare data intelligenceNoThe CMS pipelines + entity resolution are your secret sauce
IaC templates (infra/azure/)Docs onlyShow clients what's being deployed, but don't hand competitors a turnkey rival
SECURITY.md, IT-SECURITY-REVIEW.mdYes — alwaysThis accelerates client IT approvals dramatically

Timeline: Keep everything private until 3 clients are deployed and the architecture is proven. Then open source the Teams connector as a community play. By then you have case studies, domain expertise, and a Claw library that competitors can't replicate by reading your code.

Part 11 — Repo Name & Identity

The codebase name matters when IT teams Google it and when you pitch it. A few considerations:

  • Not "Chief" — that's your personal assistant name. The product needs its own identity.
  • Not your name — it should feel like a platform, not a solo developer project.
  • Should convey: intelligent, enterprise, action-oriented, M365 native.

Candidates worth considering: Echelon (executive tier), Meridian (navigates your day), Apex (executive intelligence), Vantage (elevated view of your work), Cortex (the org brain).

The GitHub org can be separate from your personal account — e.g., github.com/meridian-ai — which signals a real company, not a side project.
