OpenClaw + Microsoft Teams — Deployment Guide

Purpose: Step-by-step setup for running OpenClaw in Microsoft Teams (personal dev environment → production deployment)

Prepared: March 10, 2026 | Based on Brad Groux's production setup + OpenClaw official docs

Context: Foundation for the Enterprise AI Assistant — deploy into client Azure tenants

This afternoon's goal: Get the Microsoft environment stood up — Azure account, Azure Bot registration, Entra ID app, Teams manifest. You don't need a full running assistant today; you need the plumbing in place so you can start wiring in capabilities.

What You're Building

OpenClaw connects to Teams via the Azure Bot Service acting as a relay. The data flow is:

Teams User Message
    → Teams Bot Framework (Microsoft cloud)
    → Azure Bot (your registered bot, acts as identity + router)
    → Webhook: POST /api/messages (your OpenClaw gateway)
    → OpenClaw processes + calls tools (email, calendar, reports, etc.)
    → Response sent back via Bot Framework
    → Appears in Teams chat/channel

Your OpenClaw gateway needs to be reachable at a public HTTPS URL. For dev: a tunnel (ngrok/Cloudflare). For production (client deployments): Azure Container Apps.

Phase 1: Microsoft Account Setup

Your current blocker: Gmail tied to Microsoft account causes issues with Azure Bot tenant setup. Solution: Create a dedicated Microsoft work account — separate from your personal Gmail-linked Microsoft identity. This is what Brad hit too.

1 Create a Microsoft 365 Business account

  • Go to microsoft.com/microsoft-365/business
  • Start with Microsoft 365 Business Basic (~$6/user/month) — gives you Exchange + Teams + Entra ID
  • Use a non-Gmail email to register (create a new Outlook.com account or use a custom domain if you have one)
  • This creates your tenant: yourorg.onmicrosoft.com
  • Your Tenant ID will be visible in the Azure Portal once you sign in

If you already have an M365 account: Use the admin center to verify you have Azure Bot creation rights. If your personal Microsoft account is tied to Gmail, create a new admin user within the tenant with a @yourorg.onmicrosoft.com address.

2 Access Azure Portal

  • Go to portal.azure.com and sign in with your M365 admin account
  • You should land in your tenant — confirm at top right it shows your org domain, not a personal account
  • If prompted to create a subscription: start with the free tier (Azure Bot Service is free for dev/testing)

Phase 2: Azure Bot Registration

Important: Multi-tenant Azure Bots were deprecated after July 2025. Always create Single Tenant bots for new setups. This is also the right model for client deployments — each client gets their own bot in their own tenant.

3 Create the Azure Bot

  1. In Azure Portal → search "Azure Bot" → click Create
  2. Fill in Basics tab:
FieldValue
Bot handlechief-teams-dev (must be globally unique)
SubscriptionYour Azure subscription
Resource groupCreate new: chief-assistant-rg
Pricing tierFree (for dev)
Type of AppSingle Tenant ← critical
Creation typeCreate new Microsoft App ID

Click Review + Create → Create. Wait ~2 minutes.

4 Collect the 3 Credentials

You need exactly 3 values for OpenClaw config. Get them now and store safely:

ValueWhere to Find ItLooks Like
App IDAzure Bot → Configuration → Microsoft App IDGUID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
App Password (client secret)Azure Bot → Configuration → Manage Password → App Registration → Certificates & Secrets → New client secret → copy the Value (not the Secret ID)Long alphanumeric string
Tenant IDApp Registration → Overview → Directory (tenant) IDGUID: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
⚠️ Copy the App Password the moment you create it. Azure only shows it once. If you miss it, delete and create a new secret.

5 Set the Messaging Endpoint

Azure Bot → Configuration → Messaging Endpoint. For now, use a placeholder — you'll update this once your tunnel or server is running:

https://YOUR_TUNNEL_URL/api/messages

For local dev right now: start ngrok first (ngrok http 3978), copy the HTTPS URL, paste it here. You'll update this each dev session or set up a persistent tunnel.

6 Enable Teams Channel

  1. Azure Bot → Channels
  2. Click Microsoft Teams → Configure → Save
  3. Accept Terms of Service

This registers your bot as a Teams-enabled bot in Microsoft's system.

Phase 3: Graph API Permissions (for Email + Calendar + Files)

Basic Teams messaging only needs the Bot Service. But for the Enterprise Assistant capabilities (email triage, calendar management, file access), you need Microsoft Graph API permissions.

7 Add Graph Permissions in Entra ID

  1. Go to Entra ID (formerly Azure AD) → App Registrations → find your bot's App Registration (same App ID)
  2. Click API Permissions → Add a permission → Microsoft Graph → Application permissions
  3. Add these permissions:
PermissionWhat it EnablesPriority
Mail.ReadRead user emails (inbox triage)Day 1
Mail.SendSend emails on user's behalf (draft + send)Day 1
Calendars.ReadWriteRead + create calendar eventsDay 1
ChannelMessage.Read.AllRead Teams channel history + attachmentsDay 1
User.Read.AllResolve user names → IDs; @mention supportDay 1
Files.Read.AllRead SharePoint/OneDrive files in channelsPhase 2
Sites.ReadWrite.AllUpload files to SharePoint for group chat sharingPhase 2
Chat.Read.AllRead Teams group chat historyPhase 2

After adding permissions: click Grant admin consent for [your org]. This is a one-click button that a tenant admin must approve. For your own dev tenant, you're the admin — just click it.

Phase 4: OpenClaw Plugin + Config

8 Install the Teams Plugin

openclaw plugins install @openclaw/msteams

This was moved out of core in Jan 2026. Without this, the Teams channel won't appear in config.

9 Configure OpenClaw

Run the configure wizard (easiest) or manually edit ~/.openclaw/openclaw.json:

{
  "channels": {
    "msteams": {
      "enabled": true,
      "appId": "<YOUR_APP_ID>",
      "appPassword": "<YOUR_APP_PASSWORD>",
      "tenantId": "<YOUR_TENANT_ID>",
      "webhook": {
        "port": 3978,
        "path": "/api/messages"
      },
      "dmPolicy": "allowlist",
      "allowFrom": ["<YOUR_AAD_OBJECT_ID>"],
      "groupPolicy": "allowlist"
    }
  }
}

To find your AAD object ID (your personal user ID in the tenant): Entra ID → Users → click your user → Object ID field. This goes in allowFrom so only you can trigger the bot in DMs during dev.

10 Start Local Tunnel + Gateway

# Terminal 1 — start tunnel
ngrok http 3978
# Copy the https URL e.g. https://abc123.ngrok.io

# Update Azure Bot Messaging Endpoint to: https://abc123.ngrok.io/api/messages

# Terminal 2 — start OpenClaw
openclaw gateway start

Verify the webhook is working: Azure Bot → Test in Web Chat → send a message. If you get a response, the webhook is live. Then move to Teams.

Phase 5: Teams App Manifest

12 Sideload into Teams

  1. Open Microsoft Teams desktop app
  2. Left sidebar → Apps → Manage your apps → Upload a custom app
  3. Select your ZIP → install to your personal scope first (safer for testing)
  4. Find "Chief Assistant" in your Teams apps → send it a DM
  5. You should see a response come through OpenClaw
If sideloading is blocked by your org: Try "Upload an app to your org's app catalog" instead — this often bypasses IT sideload restrictions. Or go via Teams Admin Center → Teams apps → Manage apps.

Production Path: Azure Container Apps

For client deployments (Dave Devries / ASH and future clients), the production model is:

  1. Client provisions their Azure tenant — you help them create the Azure Bot (Single Tenant), provide the manifest, get admin consent on Graph permissions
  2. OpenClaw gateway deployed as Azure Container App — runs in their tenant, their data never leaves
  3. Environment variables hold bot credentials (MSTEAMS_APP_ID, MSTEAMS_APP_PASSWORD, MSTEAMS_TENANT_ID) — no creds in code
  4. Custom domain replaces the tunnel — Container App gets a stable HTTPS URL set as the Azure Bot Messaging Endpoint
  5. No tunnel needed — the Container App is the public endpoint
# Production config via env vars (no secrets in openclaw.json)
MSTEAMS_APP_ID=your-app-id
MSTEAMS_APP_PASSWORD=your-app-password
MSTEAMS_TENANT_ID=your-tenant-id

Client Onboarding Flow (Your Product Process)

  1. Client creates Azure subscription + M365 tenant (if they don't have one)
  2. You walk them through Azure Bot creation (30 min with this guide)
  3. Client IT admin grants Graph API permissions (admin consent button — 5 min)
  4. You deploy OpenClaw Container App into their tenant with their bot credentials
  5. You sideload or publish the Teams app package to their org catalog
  6. Client users install the app → start chatting

Total setup time: 2-4 hours first time, <1 hour for repeat clients once you have the process locked.

Brad's Production Lessons (From His Article + Bug Fix)

  • The silent message-drop bug: Debug wrappers in the compiled runtime were swallowing all channel message data. Fixed in OpenClaw 2026.3.8+ (your current version). If you're on an older version: npm update -g openclaw before any Teams work.
  • Ngrok URL changes on restart: Use a static tunnel (ngrok paid, Cloudflare Tunnel, or Tailscale Funnel) or expect to update the Azure Bot Messaging Endpoint every dev session.
  • Teams caches app metadata aggressively: After manifest changes, always: bump version number in manifest → re-zip → re-upload → fully quit + relaunch Teams (not just close window). This is the #1 "why isn't my change showing" gotcha.
  • App not responding in org: Even after sideloading, an IT admin may need to "Allow" it in Teams Admin Center. Bot appears "Offline" until this is done.
  • groupId in Teams URL ≠ team ID for config: The groupId query param in a Teams channel URL is NOT the right ID. Extract the team ID from the path segment after /team/ (URL-decode it). Same for channel IDs.
  • Reply style matters: Teams has two UI modes (Posts vs. Threads/Slack-style). Configure replyStyle: "thread" for classic Posts channels, "top-level" for Slack-like Threads channels — or replies look wrong.

Veritas Kanban — How It Relates

Brad's companion project isn't directly needed for getting Teams connected, but it shows the agent orchestration layer you'd build on top for enterprise workflows:

  • Multi-agent task dispatch: A user says "generate this week's market report" in Teams → Chief spawns sub-agents (data pull, analysis, formatting) → tracks them → returns result. That pipeline management is what Veritas Kanban handles.
  • Squad Chat protocol: Agents communicate lifecycle events (spawned/completed/failed) through a shared channel — gives humans visibility without interrupting them.
  • YAML pipelines: Define repeatable multi-step workflows (e.g., "weekly provider referral report") as YAML — sequential steps, parallel fan-out, human-in-the-loop gates.
  • Prompt registry: 10 starter templates (sprint-planning, research-report, feature-development, etc.) — same concept applies to your enterprise "Claws": templatize the common workflows your VP users will run.

You don't need to use Veritas Kanban directly, but steal the patterns: task-as-markdown-file, YAML pipelines, Squad Chat visibility layer. These map to the "Claw" architecture in your enterprise assistant.
