Executive Summary

This document provides a comprehensive overview of Cedars-Sinai's current Salesforce data integration, including the database schema, data synchronization pipeline, LLM-based enrichment layer, and reporting/analytics capabilities. This information is intended to facilitate a smooth transition to Enata's AI-enabled CRM platform while ensuring continuity of our current analytical workflows.

Integration Model: Two-Part System
  • Phase 1 (Initial): Enata ingests our existing Salesforce data structure
  • Phase 2 (Ongoing): Enata hosts the data with cron jobs to continuously sync with our Salesforce backend
  • Goal: Preserve current analytics capabilities while transitioning to Enata's platform

Salesforce Objects & Data Model

1. Core Salesforce Objects

Our integration syncs five primary Salesforce objects into corresponding PostgreSQL tables:

Salesforce Object Database Table Purpose Key Fields
User sf_users Sales reps / Business Development team members Username, Name, Email, IsActive
Account sf_accounts Organizations / Medical practices Name, Type
Contact sf_contacts Healthcare providers (physicians, staff) Name, NPI, Specialty, Geography, Network
Task + Event sf_activities BD outreach activities (merged into single table) Subject, Description, ActivityDate, MNO_Type, Owner
TaskWhoRelation sf_task_who_relations Many-to-many: Tasks linked to multiple Contacts TaskId, RelationId (ContactId)

Database Schema Details

Core Tables Schema

sf_contacts (Healthcare Providers)

Table: sf_contacts Primary Key: id (UUID) Unique: salesforce_id (Salesforce Contact.Id) Key Columns: - salesforce_id: Salesforce ID (18 chars) - name, first_name, last_name: Provider name - npi, specialty, specialty_group: Provider classification - is_physician, active: Status flags - network, sub_network, geography, primary_geography: Network/location - account_id: Link to sf_accounts - last_activity_date, last_outreach_activity_date: Activity tracking - sf_created_date, sf_last_modified_date: Salesforce timestamps - last_synced_at: Local sync timestamp Indexes: - Primary lookups: name, npi, email - Filter indexes: specialty, specialty_group, primary_geography, network, is_physician, active - Foreign key: account_id

sf_activities (Tasks + Events Combined)

Table: sf_activities Primary Key: id (UUID) Unique: salesforce_id (Salesforce Task.Id or Event.Id) Key Columns: - salesforce_id: Salesforce ID - type: 'Task' or 'Event' - subject, description: Activity content - activity_date: Date of activity - status, priority, is_closed: Task status - mno_type, mno_subtype, mno_setting: Custom BD classifications - mn_tags, comments_short: Tagging and notes - contact_id: Foreign key to sf_contacts (primary contact) - who_id, what_id, account_id, owner_id: Salesforce relationships - attendees_concatenation: All attendees - start_datetime, end_datetime, duration_minutes, location: Event fields - sf_created_date, sf_last_modified_date, last_synced_at: Timestamps Indexes: - Primary filters: activity_date + owner_id, owner_id + mno_type - Lookups: type, mno_type, mno_subtype, status, contact_id, who_id, account_id

sf_task_who_relations (Many-to-Many Junction)

Table: sf_task_who_relations Primary Key: id (int) Unique: salesforce_id Purpose: Links a single task to multiple contacts (e.g., group lunch with 3 physicians) Key Columns: - salesforce_id: Salesforce TaskWhoRelation.Id - task_id: Salesforce Task.Id - relation_id: Salesforce Contact.Id - type: Relation type - is_deleted: Soft delete flag Indexes: - task_id, relation_id, (task_id, relation_id) composite

Sync Strategy

Targeted Sync (Performance Optimization)

Rather than syncing all Salesforce data, we use a targeted approach:

  1. Contacts: Only sync contacts that have activities (via TaskWhoRelation)
  2. Accounts: Only sync accounts linked to contacts with activities
  3. Users: Only active users
  4. Activities: All tasks and events (not filtered)

Rationale: BD analysis focuses on providers we've engaged with, not the entire contact database. This reduces sync time and database size by ~70%.

Sync Modes

Mode Behavior Use Case
upsert Update existing or create new (based on salesforce_id) Default mode for incremental syncs
overwrite Clear all data, then rebuild from Salesforce Full refresh (rarely used)
incremental Only records modified since last sync Hourly/daily syncs (requires last_sync tracking)
insert_only Skip existing records, only add new Initial backfill without overwriting manual edits

LLM Enrichment Layer

The raw Salesforce data is enhanced with LLM-derived semantic fields to enable strategic analytics. This enrichment pipeline runs after sync and creates three additional tables:

1. sf_enhanced_activities (Semantic Activity Enrichments)

Purpose: Extract meaning from unstructured activity notes at scale

Enrichment Field Type Purpose Example Values
initiative_tag String Strategic program classification HRBP, TACRI_Oncology, New_Physician_Onboarding, Sports_Medicine
activity_intent String Strategic purpose First_Contact, Relationship_Building, Conversion_Attempt, Follow_Up
outcome_sentiment String How well the interaction went positive, neutral, negative, unknown
outcome_score Float Numeric sentiment score -1.0 to 1.0
outcome_key_phrase Text Phrase indicating sentiment "Great lunch, exchanged cell numbers"
relationship_stage String Pipeline stage Prospecting, Engaged, Introduced, Converted, Active_Referrer, Stalled
strategic_value Integer Activity importance (1-5) 5=conversion, 4=high-value, 3=meaningful, 2=routine, 1=admin
follow_up_needed Boolean Requires action true/false
follow_up_type String Type of follow-up Schedule_Meeting, Send_Information, Make_Introduction
next_steps Text Extracted action items "Schedule lunch with Dr. Smith"
competitor_mention Boolean Competitive intelligence flag true/false
competitor_context Text Competitive situation description "Physician currently rounds only at UCLA"
mentioned_entities JSON Extracted entities {"physicians": ["Smith"], "practices": ["UCLA"], "programs": ["HRBP"]}
onboarding_milestone String Onboarding step completed MD_Intro, SharePoint_Setup, Bio_Card, Headshot, Department_Intro

2. sf_enhanced_providers (Provider Relationship State)

Purpose: Track current relationship status and aggregate metrics per provider

Field Type Purpose
current_relationship_stage String Current stage in referral pipeline
engagement_score Float Calculated: frequency × recency × sentiment
total_activities_count Integer Number of activities with this provider
positive/neutral/negative_activities_count Integer Sentiment breakdown
avg_strategic_value Float Average activity value (1-5)
days_since_last_activity Integer For stalled relationship detection
is_new_physician Boolean New Cedars physician flag
onboarding_complete Boolean Onboarding status
onboarding_milestones_completed JSON Array ["MD_Intro", "SharePoint_Setup"]
primary_rep_id String Rep with most interactions
initiative_affinity JSON {"HRBP": 5, "TACRI": 2} - activity counts by initiative

3. sf_activity_providers (Many-to-Many Junction)

Purpose: Link activities to ALL providers involved (not just primary contact)

Why This Table Exists

A single activity (e.g., group lunch) may involve multiple providers. The junction table captures all provider-activity relationships, enabling queries like:

  • "Show all activities involving Dr. Smith" (even if not primary contact)
  • "Who attends events together?" (network analysis)
  • "What providers were mentioned in this activity's notes?"
Field Purpose
activity_id Foreign key to sf_enhanced_activities
provider_id Foreign key to sf_enhanced_providers
provider_name Denormalized for query efficiency
is_primary Boolean: primary contact vs. attendee vs. mentioned
role "primary", "attendee", "mentioned"
source "contact_id", "attendees_parsed", "notes_extracted"

⚠️ Important: Enrichment Model

Current enrichments use claude-haiku-4-5 (fast, cost-effective).

Cost estimate: ~$0.001 per activity (~$1 per 1,000 activities)

Enrichment metadata tracks model and version for auditability and re-processing if prompts change.

Reporting & Analytics Layer

MCP Server Tools (Query Layer)

Data access is provided via MCP (Model Context Protocol) server with three tool layers:

Layer 1: Foundation Tools (Query Layer)

  • mcp_query_activities - Flexible activity search with 15+ filter parameters
  • mcp_query_providers - Provider search with relationship stage, engagement filters
  • mcp_get_activity_details - Full details for single activity
  • mcp_get_provider_profile - Complete provider profile with history

Layer 2: Analytics Tools (Aggregation Layer)

  • mcp_get_initiative_metrics - Performance by initiative (HRBP, TACRI, etc.)
  • mcp_get_pipeline_analysis - Provider funnel by relationship stage
  • mcp_get_sentiment_analysis - Win/loss patterns with quotes
  • mcp_get_competitive_analysis - Competitive intelligence summary
  • mcp_get_activity_quality_analysis - Strategic value distribution

Layer 3: Intelligence Tools (Complex Insights)

  • mcp_get_rep_performance_summary - Individual rep dashboards
  • mcp_get_onboarding_dashboard - New physician progress tracking
  • mcp_find_stalled_relationships - At-risk relationships
  • mcp_get_network_map - Provider co-occurrence analysis

Salesforce Analyst Agent (Conversational Interface)

LangGraph-based ReAct agent providing natural language access to all MCP tools:

Agent Capabilities

  • Natural language queries: "What did Sara do for HRBP last quarter?"
  • Multi-step reasoning: Tool selection, data retrieval, analysis, synthesis
  • Streaming responses: Real-time token streaming to UI
  • Structured data output: DataFrames for Analyst View alongside chat
  • Excel export: Direct download of query results

Example Analytics Queries

Question Tools Used Output
"What has Jin done this quarter?" mcp_query_activities (filter: rep_name="Jin", start_date=Q1) Activity list with initiative tags, sentiment
"Show orthopedic surgeons we're engaged with" mcp_query_providers (specialty="Orthopedic", relationship_stage="Engaged") Provider list with engagement scores, recent activity

"Who needs onboarding follow-up?" mcp_get_onboarding_dashboard (onboarding_complete=false) New physicians, completed/pending milestones

Key Nuances & Recommendations for Enata

1. Data Model Nuances

⚠️ Tasks + Events Merged into Single Table

Decision: We merge Salesforce Task and Event objects into a single sf_activities table.

Rationale: BD analysis treats both as "activities" — the distinction between planned (Event) and completed (Task) is less important than the unified activity history.

Implication for Enata: If maintaining separate Task/Event tables, ensure query logic can handle both or consider adopting the merged model.

⚠️ Targeted Sync (Not Full Database)

Current approach: Only sync contacts/accounts with activities (via TaskWhoRelation).

Benefit: ~70% reduction in database size and sync time.

Trade-off: Cannot query "all providers" — only those we've engaged.

Recommendation: Maintain this targeted approach unless Enata's platform needs full contact visibility for other features.

2. Custom Field Dependencies

Critical Custom Fields (Must Preserve)

These custom Salesforce fields are core to our analytics:

  • MNO_Type__c, MNO_Subtype_c__c, MNO_Setting__c - Activity classification
  • MN_Tags__c, Comments_Short__c - Flexible tagging and notes
  • Attendees_Concatenation__c - Multi-provider activities
  • NPI__c, Specialty__c, Geography__c - Provider filtering
  • Network_picklist__c, Sub_Network__c - Network analysis
  • Last_Outreach_Activity_Date__c - Stalled relationship detection

Action: Ensure Enata's data model includes these fields or equivalent mappings.

3. LLM Enrichment Pipeline

✓ Enrichment Architecture is Portable

The enrichment pipeline is database-agnostic (SQLAlchemy ORM). Key considerations:

  • Batch processing: Nightly/weekly enrichment jobs for new activities
  • Idempotency: Enrichments can be re-run (keyed by activity_id)
  • Cost: ~$1 per 1,000 activities (Claude Haiku)
  • Performance: ~500-1000 activities/hour (API rate limits)

Recommendation: Enata can host enrichment service or we can continue running it and sync enriched data.

4. Sync Frequency & Real-time Needs

Data Layer Current Sync Frequency Real-time Required?
Core Salesforce data (Activities, Contacts) Daily (overnight) No - 24h lag acceptable
LLM enrichments Weekly (batch) No - enrichments are analytical, not operational
Provider state aggregations Weekly (after enrichment) No - used for dashboards, not day-to-day operations

Sync Recommendation

Daily overnight sync (12am-2am PST) for core data. Weekly batch enrichment (Sundays) for LLM processing. This balances freshness with API costs and processing time.

5. Reporting Continuity

⚠️ Preserve Query Patterns

Key queries we need to maintain:

  • Initiative-based filtering: "Show HRBP activities" (relies on initiative_tag)
  • Rep performance: "Sara's activities this quarter" (group by rep + date range)
  • Provider pipeline: "Engaged orthopedic surgeons" (filter by specialty + relationship stage)
  • Geographic analysis: "South Bay activities" (filter by geography)
  • Sentiment analysis: "Positive outcomes this month" (filter by sentiment)
  • Stalled relationships: "No contact in 60+ days" (calculate days_since_last_activity)

Action: Test that Enata's query layer can replicate these patterns. Provide sample queries for validation.

6. Data Quality Considerations

Issue Impact Mitigation
Inconsistent specialty naming Provider filtering unreliable Specialty standardization layer in enrichment
Multiple contacts for same provider Duplicate relationships NPI-based deduplication (NPI is unique federal ID)
Free-text geography Geographic analysis fragmented Geographic standardization (e.g., "South Bay" = Marina del Rey, Torrance, etc.)
Missing custom field values Incomplete enrichments Default values, confidence thresholds
Attendees in notes vs. TaskWhoRelation Incomplete network mapping Parse attendees_concatenation + extract from notes

7. API & Access Patterns

Current Access Methods

  • MCP Server: Tool-based access for LLM agents
  • Direct SQL: PostgreSQL queries for custom reports
  • LangGraph Agent: Natural language interface
  • Chainlit UI: Web-based chat + data tables

Recommendation: Enata should provide REST API matching MCP tool signatures for minimal code changes.

8. Enrichment Versioning & Re-processing

✓ Enrichments are Versioned

Every enriched record tracks:

  • enrichment_timestamp - When processed
  • enrichment_model - Which LLM model used
  • enrichment_version - Prompt version

Benefit: Can re-enrich historical data if prompts improve or model upgrades.

Recommendation: Maintain this metadata structure for audit trail and quality control.

9. Performance Optimization

Current Indexes (Critical for Query Performance)

The schema includes extensive indexing for common query patterns. Key composite indexes:

  • (activity_date, owner_id) - "Activities by rep over time"
  • (owner_id, mno_type) - "Rep's activity type breakdown"
  • (initiative_tag, activity_date) - "Initiative performance over time"
  • (current_relationship_stage, geography) - "Pipeline by territory"
  • (is_new_physician, onboarding_complete) - "Onboarding status"

Action: Ensure Enata's database preserves these indexes or equivalents.
