Approach 1: SSH + Docker Remote Context

How It Works

Docker natively supports running containers on remote hosts over SSH. You configure a "context" pointing to Dave's machine, and all docker commands execute there instead of locally.

# Dave's side (one-time setup)
# 1. Enable SSH with key-based auth
ssh-keygen -t ed25519  # Generate SSH key
cat ~/.ssh/id_ed25519.pub  # Share public key with Blake

# 2. Blake adds Dave's key to authorized_keys
echo "ssh-ed25519 AAAA...dave@dave-mac" >> ~/.ssh/authorized_keys

# 3. Verify Docker is installed and running
docker ps

# Blake's side (every time)
# Create remote context
docker context create dave-mac \\
  --description "Dave's Mac Mini" \\
  --docker "host=ssh://blake@192.168.1.100"

# Switch to remote context
docker context use dave-mac

# Now all docker commands run on Dave's machine
docker run -m 16g --rm my-agent-workload
docker ps  # Shows containers running on Dave's machine

# Switch back to local
docker context use default

Pros & Cons

✅ Pros

  • Works today: Zero new software, uses existing Docker + SSH
  • Secure: SSH encryption, key-based auth, proven security model
  • Simple: Minimal setup, easy to understand
  • Full control: Dave can see exactly what's running (docker ps)
  • No cloud dependency: Works on local network or over internet

❌ Cons

  • Manual IP management: Need Dave's IP address (changes if on DHCP)
  • No discovery: Blake has to know Dave's machine exists and is available
  • No payment system: Settlement is manual (Venmo, PayPal)
  • Network dependency: If Dave's machine is behind firewall, needs port forwarding
  • Single point of failure: If Dave's machine goes down, job fails

Technical Details

Aspect Implementation
Transport SSH (encrypted, authenticated)
Isolation Docker containers (cgroups, namespaces)
Resource limits docker run -m 16g --cpus 4 (enforced by kernel)
Networking Bridge network (containers can't access host network by default)
Storage Container filesystem (ephemeral unless volumes mounted)
Monitoring docker stats (CPU, RAM, network usage)

Security Considerations

What Blake CAN do:

  • Run any Docker image on Dave's machine
  • Execute commands inside containers
  • Read container logs
  • Copy files in/out of containers

What Blake CANNOT do (without explicit permission):

  • Access Dave's filesystem outside containers
  • See Dave's other processes
  • Access Dave's home network
  • Modify Dave's system configuration

Risk: Blake runs a malicious container

# Malicious example (DON'T DO THIS)
docker run -v /:/host-root alpine cat /host-root/Users/dave/.ssh/id_rsa

Mitigation: Dave should restrict what Blake can mount. Use docker-compose with pre-approved volumes only.

When to Use This

  • ✅ You trust the person (friend, colleague)
  • ✅ You only have 2-3 hosts
  • ✅ You want to test the concept quickly
  • ✅ You don't need automated discovery or payment

Recommendation for Blake: Start here to validate demand with 2-3 friends this week.

Approach 2: Tailscale + Docker Remote

How It Works

Tailscale creates a private VPN (mesh network) between your devices. Each machine gets a persistent IP (100.x.x.x) that's accessible from anywhere. You then use Docker remote context over Tailscale IPs.

# Both Blake and Dave install Tailscale
brew install tailscale
sudo tailscale up

# Tailscale assigns persistent IPs:
# Blake's laptop: 100.64.0.10
# Dave's Mac Mini: 100.64.0.5

# Blake creates Docker context using Tailscale IP
docker context create dave-mac \\
  --docker "host=ssh://blake@100.64.0.5"

# Now works from anywhere (not just home network)
docker context use dave-mac
docker run my-workload

Pros & Cons

✅ Pros

  • Works from anywhere: Not tied to local network, can access Dave's machine from coffee shop
  • Persistent IPs: Tailscale IPs don't change (100.x.x.x)
  • Encrypted: WireGuard encryption (fast, modern)
  • Easy setup: Install app, sign in, done (5 minutes)
  • Free for personal use: Up to 100 devices, no cost
  • NAT traversal: Works even if Dave is behind router/firewall

❌ Cons

  • Still no discovery: Blake has to know Dave's Tailscale IP
  • Still no payment: Manual settlement
  • Trust required: Tailscale gives full network access (not just Docker)
  • Dependency on Tailscale: If Tailscale goes down, connectivity breaks
  • Account required: Both need Tailscale accounts

Technical Details

Aspect Implementation
Transport WireGuard VPN (Tailscale mesh network)
IP allocation 100.x.x.x CGNAT range (persistent)
Firewall traversal DERP relay servers (works behind NAT)
Encryption WireGuard (Noise protocol framework)
Isolation Docker containers (same as Approach 1)
Access control Tailscale ACLs (can restrict which machines talk to each other)

Advanced: Tailscale ACLs for Security

// Tailscale ACL policy (JSON)
{
  "acls": [
    {
      "action": "accept",
      "src": ["blake@example.com"],
      "dst": ["dave-mac:22", "dave-mac:2375"],  // SSH + Docker
    },
    {
      "action": "accept",
      "src": ["dave@example.com"],
      "dst": ["blake-laptop:*"],
    }
  ]
}

This restricts Blake to only SSH and Docker access on Dave's machine (not full network access).

When to Use This

  • ✅ You want to access Dave's machine from anywhere (not just home network)
  • ✅ You have 3-10 hosts in your network
  • ✅ You want persistent IPs (no dynamic DNS headaches)
  • ✅ You're comfortable with a third-party VPN service

Recommendation for Blake: Best MVP approach for a small friends network. Use this to build initial product.

Approach 3: Docker Swarm

How It Works

Docker Swarm is Docker's native orchestration mode. You create a "swarm" (cluster) of machines, designate managers and workers, and deploy services that automatically distribute across hosts.

# Dave's machine - initialize swarm
docker swarm init --advertise-addr 192.168.1.100

# Output: join token for workers
# To add a worker: docker swarm join --token SWMTKN-1-...

# Blake's laptop - join as worker (optional, or just manager)
docker swarm join --token SWMTKN-1-... 192.168.1.100:2377

# Now deploy a service (runs on any available node)
docker service create \\
  --name blake-agents \\
  --replicas 5 \\
  --constraint 'node.hostname==dave-mac' \\
  --reserve-memory 16g \\
  my-agent-image

# Check where containers are running
docker service ps blake-agents

# Scale up/down
docker service scale blake-agents=10

Pros & Cons

✅ Pros

  • Built into Docker: No additional software, native orchestration
  • Service discovery: Containers can find each other by name
  • Load balancing: Distribute workloads across multiple hosts
  • Health checks: Restart failed containers automatically
  • Rolling updates: Deploy new versions without downtime
  • Secrets management: Securely pass credentials to containers

❌ Cons

  • More complex setup: Need to understand manager/worker roles
  • Port management: Opens ports 2377, 7946, 4789 (security concern)
  • Still no payment: Manual settlement
  • Fixed cluster: Hosts join permanently, not ephemeral rentals
  • Declining adoption: Docker Inc deprioritized Swarm in favor of Kubernetes

Technical Details

Component Purpose Port
Manager node Orchestrates cluster, schedules tasks 2377/tcp
Worker node Runs containers assigned by manager —
Gossip network Service discovery, health checks 7946/tcp+udp
Overlay network Encrypted container-to-container traffic 4789/udp

Resource Constraints

# Service with resource limits
docker service create \\
  --name data-processing \\
  --replicas 3 \\
  --reserve-memory 4g \\
  --limit-memory 8g \\
  --reserve-cpu 2 \\
  --limit-cpu 4 \\
  my-heavy-workload

When to Use This

  • ✅ You have a small team (3-5 people) pooling resources
  • ✅ Hosts are semi-permanent (not ephemeral rentals)
  • ✅ You want automatic failover and health monitoring
  • ✅ You're already familiar with Docker and don't want to learn Kubernetes

Recommendation for Blake: Overkill for peer-to-peer rentals. Better for a small team with dedicated infrastructure.

Approach 4: HashiCorp Nomad

How It Works

Nomad is a lightweight alternative to Kubernetes for scheduling jobs across multiple machines. It's simpler than Kubernetes but more powerful than Docker Swarm.

# Install Nomad on all machines
brew install nomad

# Dave's machine - start Nomad server
nomad agent -server -bootstrap-expect=1 -data-dir=/tmp/nomad

# Blake's laptop - start Nomad client (connects to Dave's server)
nomad agent -client -servers=192.168.1.100:4647 -data-dir=/tmp/nomad

# Define a job (job.hcl)
job "blake-agents" {
  datacenters = ["dc1"]
  
  group "agents" {
    count = 5
    
    task "agent" {
      driver = "docker"
      
      config {
        image = "my-agent-image"
        memory_hard_limit = 3200  # 3.2GB per agent
      }
      
      resources {
        cpu    = 500  # MHz
        memory = 2048 # MB
      }
    }
  }
}

# Submit job to cluster
nomad job run job.hcl

# Check status
nomad status blake-agents

Pros & Cons

✅ Pros

  • Multi-cloud: Can mix AWS, Dave's Mac, and your laptop in one cluster
  • Multiple workload types: Docker, Java, binaries, VMs
  • Better scheduling: Smarter placement than Docker Swarm
  • Good for batch jobs: Designed for ephemeral workloads
  • Integrates with Consul, Vault: Service discovery, secrets management
  • Active development: HashiCorp maintains it (unlike Docker Swarm)

❌ Cons

  • Learning curve: More concepts to learn (jobs, task groups, allocations)
  • Overkill for small setups: Complex for 2-3 machines
  • Still no payment: Manual settlement
  • Requires dedicated server: Nomad server needs to run 24/7

Technical Details

Component Purpose
Nomad Server Cluster orchestration, job scheduling, leader election
Nomad Client Runs on worker machines, executes tasks
Job Declarative spec for what to run (like Kubernetes Deployment)
Task Group Set of tasks that run together on same machine
Allocation Instance of a task group running on a client

When to Use This

  • ✅ You need to orchestrate workloads across AWS + local machines
  • ✅ You want better scheduling than Docker Swarm
  • ✅ You're already using HashiCorp tools (Consul, Vault, Terraform)
  • ✅ You have experience with cluster orchestration

Recommendation for Blake: Only if you need multi-cloud orchestration. Too complex for a simple peer-to-peer marketplace MVP.

Approach 5: Custom Marketplace Platform

Architecture Overview

Build a purpose-built platform with host daemon, central registry, renter CLI, and automated payment/discovery.

Components

Component Technology Purpose
Host Daemon Go (or Rust) Monitors resources, accepts jobs, reports usage
Central Registry FastAPI (Python) Lists available hosts, matches renters
Renter CLI Python or Go Search, rent, deploy workloads
Payment Service Stripe API Escrow, settlement, payouts
Database PostgreSQL Hosts, users, transactions, ratings
Workload Transport Docker over SSH Deploy containers to remote hosts

Data Flow

1. Host (Dave) starts daemon
   └─> Registers with central registry
   └─> Publishes availability (16GB RAM, $0.50/hour)

2. Renter (Blake) searches marketplace
   └─> Queries central registry
   └─> Sees Dave's machine available

3. Blake rents Dave's machine
   └─> Payment held in escrow (Stripe)
   └─> Registry returns Dave's connection details

4. Blake deploys workload
   └─> CLI uploads Docker image to Dave's daemon
   └─> Daemon runs container, reports usage

5. Job completes
   └─> Daemon notifies registry
   └─> Registry triggers payment release to Dave
   └─> Blake downloads results

Host Daemon (Pseudocode)

// host_daemon.go
package main

func main() {
    // Load config
    config := loadConfig()  // RAM limit, price, trust list
    
    // Register with central registry
    registerHost(config)
    
    // Start API server
    http.HandleFunc("/api/run", handleRunJob)
    http.HandleFunc("/api/status", handleStatus)
    http.ListenAndServe(":9000", nil)
    
    // Background: monitor resources
    go monitorResources()
    
    // Background: heartbeat to registry
    go heartbeat()
}

func handleRunJob(w http.ResponseWriter, r *http.Request) {
    // 1. Verify renter is authorized
    if !isAuthorized(r.Header.Get("X-Renter-ID")) {
        http.Error(w, "Unauthorized", 401)
        return
    }
    
    // 2. Check resources available
    if !hasCapacity(r.RAM, r.CPU) {
        http.Error(w, "Insufficient resources", 503)
        return
    }
    
    // 3. Pull Docker image
    docker.Pull(r.Image)
    
    // 4. Run container with limits
    containerID := docker.Run(
        image: r.Image,
        memory: r.RAM,
        cpus: r.CPU,
        networkMode: "none",  // Isolated
    )
    
    // 5. Monitor and report usage
    go reportUsage(containerID)
    
    w.Write(containerID)
}

Central Registry API

# registry_api.py (FastAPI)
from fastapi import FastAPI
from typing import List

app = FastAPI()

@app.get("/hosts/search")
def search_hosts(ram_gb: int, location: str = None) -> List[Host]:
    """Find available hosts matching requirements"""
    query = db.query(Host).filter(
        Host.available_ram >= ram_gb,
        Host.status == "online"
    )
    
    if location:
        query = query.filter(Host.location == location)
    
    return query.order_by(Host.price_per_hour).all()

@app.post("/rentals")
def create_rental(renter_id: str, host_id: str, specs: dict):
    """Create rental, hold payment in escrow"""
    # 1. Verify host has capacity
    host = db.query(Host).get(host_id)
    if host.available_ram < specs['ram']:
        raise HTTPException(400, "Insufficient capacity")
    
    # 2. Hold payment in escrow
    payment = stripe.PaymentIntent.create(
        amount=calculate_cost(host, specs),
        currency="usd",
        customer=renter_id,
        capture_method="manual"  # Escrow
    )
    
    # 3. Create rental record
    rental = Rental(
        renter_id=renter_id,
        host_id=host_id,
        specs=specs,
        payment_intent=payment.id,
        status="active"
    )
    db.add(rental)
    db.commit()
    
    # 4. Return connection details
    return {
        "rental_id": rental.id,
        "host_ip": host.tailscale_ip,
        "ssh_key": host.public_key
    }
