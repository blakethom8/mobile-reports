3. His GitHub: Veritas Kanban

Brad's flagship project is Veritas Kanban (544 stars, 51 forks) — a lightweight, file-based orchestration platform for agentic AI, explicitly built and tested with OpenClaw.

What Veritas Kanban Does

Think of it as GitHub Actions — but for AI agents. Tasks are markdown files. Workflows are YAML. No database, no Docker, no Redis. Everything is grep-friendly and version-controlled.

  • Multi-agent dashboard — spawn OpenClaw agents on tasks, track status in real-time, model attribution (Claude vs GPT), expandable agent cards
  • Squad Chat protocol — agents share a communication channel with lifecycle events (spawned/completed/failed)
  • YAML pipelines — sequential steps, parallel fan-out/fan-in, loop iteration, human-in-the-loop gates, retry routing
  • MCP Server — 26 tools across 6 categories via Model Context Protocol
  • Task dependency graphs — with cycle detection, crash-recovery checkpointing, observational memory with importance scoring
  • Git worktrees per task — no branch switching conflicts; built-in code review with diff viewer, inline comments, approval workflows
  • OpenClaw native — uses sessions_spawn for agent orchestration; designed as a companion layer

His other repos (8 total, most private) include the openclaw/openclaw repo pinned — confirming his maintainer role.

4. OpenClaw Teams Integration — How It Actually Works

This is pulled directly from the local OpenClaw docs (/opt/homebrew/lib/node_modules/openclaw/docs/channels/msteams.md, updated 2026-01-21).

Architecture

  • Ships as a separate plugin (moved out of core in 2026.1.15): openclaw plugins install @openclaw/msteams
  • Connects via Azure Bot Service → Bot Framework webhook → OpenClaw gateway
  • Bot listens on /api/messages (port 3978 by default)
  • Requires a Teams app manifest (ZIP package) sideloaded into Teams

Credential Setup (3 values needed)

ValueWhere to Get ItConfig Key
App IDAzure Bot → ConfigurationappId
App Password (client secret)Azure Bot → Manage Password → App Registration → Certificates & SecretsappPassword
Tenant IDApp Registration → Overview → Directory (tenant) IDtenantId
Deprecation Note: Multi-tenant bots were deprecated after 2025-07-31. New bots must use Single Tenant type. This matters for your Azure account setup.

Minimal Config

{
  channels: {
    msteams: {
      enabled: true,
      appId: "<APP_ID>",
      appPassword: "<APP_PASSWORD>",
      tenantId: "<TENANT_ID>",
      webhook: { port: 3978, path: "/api/messages" }
    }
  }
}

RSC Permissions (Teams Manifest)

The app manifest defines what the bot can read/send in Teams. Key RSC permissions:

PermissionScopeWhat It Enables
ChannelMessage.Read.GroupTeam channelsReceive all channel messages without @mention
ChannelMessage.Send.GroupTeam channelsSend to channels
ChatMessage.Read.ChatGroup chatsReceive all group chat messages without @mention
Member.Read.Group + TeamMember.Read.GroupBothRoster access

RSC-Only vs. Graph API

CapabilityRSC Only+ Graph API
Real-time messages✅ Yes (webhook)✅ Yes
Message history❌ No✅ Yes (ChannelMessage.Read.All)
Attachments/images in channels❌ No (HTML stub only)✅ Yes (downloads from SharePoint/OneDrive)
File sending in group chats❌ No✅ Yes (needs sharePointSiteId)
Admin consent requiredNo✅ Yes

Access Control

  • DMs: Default is dmPolicy: "pairing" — unknown senders ignored until approved. Allowlist uses AAD object IDs (not email/name — those are mutable).
  • Groups/Channels: Default is groupPolicy: "allowlist" — blocked unless you configure groupAllowFrom. Or set groupPolicy: "open" with mention gating.
  • Per-team/channel tools: You can configure which tools are allowed per team, per channel, per sender — very granular.

Sessions & Routing

  • DMs → main session (user tied to their AAD object ID)
  • Channel messages → isolated session per conversation: agent:<id>:msteams:channel:<conversationId>
  • Replies always go back to the channel they came from

Adaptive Cards

Polls and arbitrary rich cards are sent as Adaptive Cards (Teams has no native poll API). Cards can be sent to users or conversation IDs via the message tool or CLI.

Local Development Tunneling

Teams can't reach localhost. Options: ngrok (ngrok http 3978) or Tailscale Funnel. Set the Azure Bot Messaging Endpoint to the tunnel URL.

5. Brad's Enterprise Setup Guide (openclawforge.com)

His article at openclawforge.com covers the enterprise angle specifically:

  • Why OpenClaw over standard Teams bots: Standard bots are rigid linear logic (slash commands only). OpenClaw is agentic — it monitors channels, identifies needs, and executes multi-step sequences across APIs. Modularity is the key differentiator.
  • Data sovereignty angle: OpenClaw routes LLM interactions through your own infrastructure — sensitive corporate data doesn't hit public model training sets. Directly addresses healthcare compliance concerns.
  • Recommended skills for enterprise Teams:
    • PDF summarization (drop report → instant executive summary)
    • GitHub integration (PR monitoring, issue summaries)
    • Meeting management (action items from transcriptions)
    • Natural language SQL queries against internal databases
    • Notification routing (filter DevOps alerts into specific channels)
  • Security model: Restrict by Tenant ID in Azure Bot Service; OAuth2 for high-stakes skills; dedicated gateway for audit logging; principle of least privilege
  • Common gotchas: Ngrok URL changes after restart (use static reverse proxy); Teams Admin Center must explicitly "Allow" the app org-wide (not just sideloaded); don't overload with too many skills at once

Key Insights for Your Build

  1. The silent message-drop bug Brad fixed is important. Brad fixed a bug where every channel message was being silently dropped since the last update. If you're deploying this to Dave Devries or other clients, you need Brad's patched version — make sure you're on OpenClaw 2026.3.8 or higher (your current version) which should include this fix.
  2. Single Tenant is the right call for enterprise deployments. Multi-tenant bots are deprecated. Each client gets their own Azure Bot in their own tenant — this actually aligns perfectly with your "deploy inside client's Azure tenant" model and eliminates shared credential risk.
  3. Graph API permissions are required for the assistant capabilities you want. RSC-only gives you real-time message receiving. But email (Graph), calendar (Graph), file access (Graph + SharePoint) — all of those need admin consent in the client's tenant. The Graph permission set you need: Mail.Read, Mail.Send, Calendars.ReadWrite, Files.Read.All, ChannelMessage.Read.All, User.Read.All.
  4. Per-team/channel tool policies = product feature. OpenClaw allows tools config per team, channel, and sender. This is your access control model for enterprise — a VP gets different tool access than a manager. Document this as a product capability.
  5. Veritas Kanban is worth studying closely. For multi-agent orchestration within Teams (spawning sub-agents for longer tasks, tracking them, routing results back), his YAML pipeline model and Squad Chat protocol are exactly the kind of patterns you'd want for the "Claw" architecture. No need to reinvent this wheel.
  6. Azure account blocker = same blocker Brad had. The Gmail-tied Microsoft account issue you hit is a common friction point. Brad dealt with this too. Solution: create a new Microsoft account with a non-Gmail address for the Azure Bot registration, separate from your personal M365 login. The bot itself doesn't need to be tied to your personal identity.
