🏗️ Prediction Market Platform Architecture

Prepared by Chief | March 18, 2026

Research platform + execution system for Kalshi / later Polymarket

Goal: build a platform that can (1) ingest market + external data, (2) run repeatable ML research loops, (3) backtest strategies honestly, and (4) later execute live trades with risk controls. This is not just a bot — it's a full research and trading platform.

Platform Thesis

The platform should be optimized for one thing: finding and exploiting market mispricing. That means the system is built around:

  • Data warehousing — historical market + external features
  • Research loops — fixed evaluator, editable signal logic
  • Backtesting — honest simulation with fees/spreads/capital limits
  • Execution — later, live order placement with hard risk controls

Core Design Principle

We are not building a generic “AI trading bot.” We are building a domain-aware mispricing engine with a clean separation between data, research, backtesting, and live execution.

2. Warehouse Layer

Central storage should be DuckDB + Parquet, same philosophy as the CMS work.

Responsibilities:

  • Keep raw and normalized layers separate
  • Create time-aligned market state tables
  • Support both analytics and ML feature generation

3. Feature Engineering Layer

This is where raw data becomes something usable by signals and models.

Cross-market structuresum-to-one deviations, sibling bracket inconsistencies, related market spreads
Domain featuresweather model consensus, CPI leading indicators, claims release calendars

4. Research Layer

This copies the best part of the CMS fraud detector.

eval.py # FIXED evaluator / backtester signal.py # editable rule/model logic results.tsv # experiment log strategies/ # prompt/strategy docs for agents reports/ # HTML outputs

Responsibilities:

  • Run experiments repeatedly
  • Record metrics every time
  • Let us improve signals without changing the oracle

5. Model Layer

We should support multiple model classes, not force one worldview too early.

Model TypeRole
Rule-based signalsBaselines and sanity checks
Tree/boosting modelsBest early structured-data learners
Sequence modelsKarpathy-style later-stage research
LLM-assisted modelsNarrative / mention / event-driven markets

6. Backtest / Simulation Layer

This is the most important integrity layer.

Must simulate:

  • fees
  • bid/ask spread
  • position sizing
  • capital constraints
  • daily/weekly stop-losses
  • time-based exits
  • no lookahead leakage
Non-negotiable: if a model only works in a frictionless backtest, it doesn't work.

7. Execution Layer

This comes after research and backtesting are trustworthy.

Responsibilities:

  • read live Kalshi market data
  • run signal inference
  • compute size using Kelly / fractional Kelly
  • place orders with hard caps
  • log every action
  • support paper-trading and live mode separately

8. Monitoring / Control Layer

  • P&L dashboard
  • Open positions
  • Model decisions / feature snapshots
  • Error alerts
  • Kill switch

Research Architecture

Fixed Evaluator

eval.py should be sacred, same as the fraud detector.

It should:

  • load a historical slice of market states
  • call signal.py or model logic
  • simulate trades with fees/spreads/sizing
  • score results with fixed metrics
  • append to results.tsv

Editable Signal Layer

signal.py starts simple:

  • input: feature row or market state sequence
  • output: fair probability, expected edge, and trade/no-trade

Risk Controls Must Be Platform-Level, Not Model-Level

Even if the model goes off the rails, the platform should still stop it from blowing up the bankroll. Hard caps, daily loss limits, and max exposure live outside the model.

What We Are Deciding Later

The architecture intentionally does not hardcode the first betting domain yet. It supports:

  • weather
  • macro / CPI / jobs / Fed
  • financial thresholds
  • later, political / narrative markets

The next discussion is about which external datasets plug into this architecture first, not whether the architecture itself works.

Recommendation: build the platform once, choose the first domain second. That keeps us from hardcoding everything around weather too early if we later decide macro is the better edge.
